# FatVPN BFF — контракт API

> Источник: раздел 8 `VPN-App-Project.md`.

## Статус: все эндпоинты реализованы

Все эндпоинты реализованы в `backend/src/FatVpn.Bff.Api/Controllers`.

Проверено end-to-end на тестовом сервере (87.121.221.229, тестовый бот `@testfatvpnnbot` — это не прод):
- Бот нажимает «Поменять ключ» → регистрирует 32-символьный токен через `POST /internal/tokens`
- `POST /auth/token` возвращает JWT
- `GET /config` проксирует сырую подписку Remnawave с правильным Content-Type
- `GET /servers` возвращает список из 10 стран / 36 нод

Pairing-эндпоинты (`/pair/*`, `/internal/pair/complete`, `/internal/account/subscription`) — **задеплоены на тестовый сервер и проверены** (2026-07-06): pairing-цикл curl-ом, проводка бот→BFF, полный e2e на реальном телефоне (см. `docs/app-bff-integration.md`). BFF там выставлен наружу по HTTP (`http://87.121.221.229:5030`).

Проверено end-to-end только локально (не на проде, 2026-07-05):
- `POST /trial` — MVP-версия, см. подробности и открытые вопросы ниже.

**Секреты не хранятся в git.** На новой машине (и обязательно на проде!) перед запуском выполнить:

```
cd backend/src/FatVpn.Bff.Api
dotnet user-secrets set "Remnawave:ApiToken" "<токен из панели>"
dotnet user-secrets set "Trial:DeviceKeySalt" "<случайная строка>"
```

`Jwt:Secret` и `Bot:Secret` для локальной разработки — в `appsettings.Development.json`. Файл
**больше не в git** (шаблон — `appsettings.Development.example.json`), потому что попадал ещё и
в docker-образ: одной переменной `ASPNETCORE_ENVIRONMENT=Development` на сервере хватило бы,
чтобы BFF начал подписывать JWT общеизвестным ключом. Значения, которые лежали в нём
раньше, надо считать публичными. На всякий случай Development-конфигурация теперь **отказывается
стартовать** на не-loopback адресе.

## ⛔ Обязательные переменные окружения (иначе контейнер не поднимется)

Конфигурация проверяется на старте (`ValidateOnStart`), до подключения к БД. Вне Development
приложение **падает с внятным сообщением**, если чего-то нет — это сделано намеренно: раньше
пустой `Jwt:Secret` давал 500 на каждом логине уже в рантайме.

| Переменная | Требование |
|---|---|
| `Jwt__Secret` | ≥ 32 байт |
| `Bot__Secret` | ≥ 16 символов |
| `Remnawave__ApiToken` | непустой |
| `Trial__DeviceKeySalt` | непустой — **новое требование**, раньше пустая соль молча проглатывалась |

`Trial__DeviceKeySalt` добавлен в `backend/docker-compose.yml` как `${TRIAL_DEVICE_KEY_SALT}`.
**Задать перед первым деплоем этих изменений**, иначе `docker compose up -d bff` уйдёт в
crash-loop.

## Новые необязательные настройки

| Ключ | По умолчанию | Зачем |
|---|---|---|
| `Security:RequireHttps` | `false` | Включает `UseHttpsRedirection` + HSTS. Держится выключенным до тех пор, пока приложение не переедет на `https://`-адрес: иначе каждый уже установленный клиент упрётся в 307. Требует заполненного `ReverseProxy`. |
| `ReverseProxy:KnownProxies` / `KnownNetworks` | пусто | Кому доверять `X-Forwarded-For`. Пусто = никому, и тогда per-IP лимиты складывают всех клиентов за Caddy в один бакет. В compose проставлено `172.16.0.0/12` (docker-мост). |
| `RateLimiting:*` | 300/мин глобально, 20/мин auth, 60/мин `/pair/status`, 5/час `/trial` | Лимиты вынесены в конфиг, потому что за carrier-NAT правильные числа зависят от площадки. `Enabled: false` выключает целиком. |
| `Jwt:RefreshGraceWindow` | 30 с | Окно, в котором повторное предъявление только что отротированного refresh-токена считается гонкой клиента, а не кражей (см. «Модель токенов»). |
| `Jwt:AbsoluteSessionLifetime` | `00:00:00` (выкл) | Потолок жизни сессии независимо от ротаций. Включение разлогинит всех, кто его перешагнул, — это продуктовое решение. |
| `Remnawave:HysteriaHosts` | FR/US/FI | Хосты Hysteria2 больше не захардкожены в коде. |

## Общие правила ответов (действуют с `820b1fe`)

Касаются **всех** эндпоинтов, поэтому вынесены сюда, а не продублированы в каждом.

| Код | Когда | Что видит клиент |
|---|---|---|
| **429** | Превышен per-IP лимит (`RateLimiting:*`) | Заголовок `Retry-After` в секундах. Приложение обязано его уважать, а не ретраить в цикле |
| **502** | Любой сбой обращения к Remnawave — таймаут (10 с), не-2xx, не-JSON (страница Cloudflare) | `ProblemDetails` c `title: "Upstream unavailable"`. Раньше эти случаи давали 500 |
| **413** | Тело запроса больше 64 КБ (`Kestrel.Limits.MaxRequestBodySize`) | — |
| **400** | Не прошла валидация DTO (`StringLength`) или явная проверка контроллера | `ProblemDetails` |
| **500** | Больше **не** должен появляться на путях «панель недоступна» и «JWT без claim» — если появился, это баг |

Прочее:

- Ответы `/servers` и `/config` сжимаются (`AddResponseCompression`, gzip/brotli).
- `GET /health` теперь проверяет БД: `{"status":"ok"}` при живой базе, `{"status":"degraded"}`
  при мёртвой (форма ответа сохранена, чтобы существующие пробы не переписывать).
- Отклонённый вызов `/internal/*` с неверным или отсутствующим `X-Bot-Secret` → **401**
  (проверка вынесена в политику авторизации `Bot`, а не копипастится в контроллерах).

## Модель токенов (важно)

С релиза refresh-split (2026-07-08) сессия — это **пара токенов**:

- **`accessToken`** — короткоживущий JWT (**30 мин**, `Jwt:AccessTokenLifetime`).
  Срок жизни **развязан** со сроком подписки: JWT отвечает «кто ты», а право
  доступа проверяется **живьём** в каждом запросе. Claim — `fatvpn_account_id`
  (pairing) или `fatvpn_token_id` (legacy/trial).
- **`refreshToken`** — долгоживущий (**90 дней**, `Jwt:RefreshTokenLifetime`),
  **отзываемый**, **ротируемый** непрозрачный секрет. В БД хранится только его
  SHA-256-хеш; сырое значение отдаётся клиенту один раз. Приложение меняет его
  на свежий access через `/auth/refresh`.
- **Истечение подписки:** `accessToken` НЕ протухает вместе с подпиской (в отличие
  от старой схемы). Вместо этого `/config` и `/servers` при истёкшей подписке
  отдают **402 Payment Required**, а `/me` — `status: "expired"`. Так приложение
  отличает «нужно продлить» (402) от «токен невалиден» (401) и ведёт на экран
  продления, а не на онбординг.

## Публичные эндпоинты (мобильное приложение)

### `POST /auth/token`
Обмен короткого токена (полученного из Telegram-бота) на пару токенов.

- **Запрос:** `{ "shortToken": string, "attestationToken": string? }`
- **Ответ:** `{ "accessToken": string, "refreshToken": string, "expiresAt": datetime, "subscriptionExpiresAt": datetime, "accessTokenExpiresAt": datetime }`
- **Ошибки:** 404 — токен не найден/просрочен; 409 — ключ уже привязан к другому телефону; 429 — превышен лимит (20/мин на IP)
- **`attestationToken` (опционально) — это привязка «один ключ = один телефон».** Первое
  устройство, погасившее ключ, привязывает его к своему хешу устройства; другое устройство
  с тем же ключом получает **409**. Привязка выполняется одним условным `UPDATE`, поэтому
  два телефона, вводящие ключ одновременно, больше не привязываются оба. Если поле не
  прислано или пустое — сессия выдаётся **без** привязки (так продолжают работать старые
  сборки приложения). Повторная регистрация ключа ботом (`POST /internal/tokens`, «Поменять
  ключ») сбрасывает привязку.
- **`expiresAt` — это срок подписки, а не access-токена.** Поля `subscriptionExpiresAt` и
  `accessTokenExpiresAt` добавлены, чтобы приложение перестало рефрешить по чужим часам;
  старое `expiresAt` оставлено как есть, чтобы уже выпущенные сборки продолжали работать.
- ⚠️ **`accessTokenExpiresAt` отдают только `/auth/token` и `/auth/refresh`.**
  `/pair/status` и `/trial` его **не** возвращают, поэтому приложению нужен фолбэк
  (парсить `exp` из JWT либо считать «access живёт 30 мин от момента выдачи»).

### `POST /auth/refresh`
Обмен refresh-токена на свежий access (с ротацией refresh). Право подписки здесь
**не** проверяется — истёкшая подписка тоже должна уметь рефрешить, чтобы дойти до
экрана продления и подхватить будущее продление.

- **Запрос:** `{ "refreshToken": string }`
- **Ответ:** `{ "accessToken": string, "refreshToken": string, "expiresAt": datetime, "subscriptionExpiresAt": datetime, "accessTokenExpiresAt": datetime }`
- **Ошибки:** 401 — refresh неизвестен / отозван / истёк (приложение выходит на онбординг); 429 — лимит
- **Защита от повторного использования:** предъявление уже отозванного (но не истёкшего) refresh-токена трактуется как кража — отзывается **вся семья** активных refresh-токенов этой сессии (аккаунта/токена), и и вор, и владелец вынуждены заново пройти pairing.
- **Grace-окно (`Jwt:RefreshGraceWindow`, 30 с).** Приложение спокойно шлёт два-три
  `/auth/refresh` одновременно, когда несколько запросов упираются в 401 разом. Раньше
  проигравший гонку предъявлял только что отротированный токен, и это срабатывало как
  кража — пользователя выкидывало из оплаченной подписки. Теперь предъявление в пределах
  окна считается гонкой клиента: семья не отзывается, выдаётся ещё один токен той же
  семьи. Заметьте: **не тот же самый** токен, что вернул победитель гонки — refresh-токены
  хранятся только хешами, восстановить исходное значение неоткуда. Клиенту достаточно
  сохранить последний полученный.
- **Ротация теперь атомарна** (`UPDATE ... WHERE RevokedAt IS NULL`): два параллельных
  вызова больше не могут оба «повернуть» один токен и оставить в базе две живые сессии.

### `POST /auth/logout`
Best-effort отзыв refresh-токена при выходе. Всегда 204 (нельзя пробить, какие токены существуют).

- **Запрос:** `{ "refreshToken": string }`
- **Ответ:** 204 No Content

### `POST /pair/start`
Приложение начинает pairing (связывание по одноразовому коду). Показывает `pairCode`/QR и открывает бота ссылкой `t.me/<bot>?start=pair<pairCode>`.

- **Запрос:** тело не требуется
- **Ответ:** `{ "pairCode": string, "pollToken": string, "expiresAt": datetime }` (это pairing-`expiresAt` — срок жизни кода, не подписки)
- `pairCode` — 8 символов (base32 без похожих букв), уходит в Telegram deep link.
- `pollToken` — секрет устройства, с которым приложение опрашивает статус. Не передаётся в чат.
- Код живёт 15 минут.

### `GET /pair/status?pollToken=<...>`

> Токен можно (и лучше) передавать заголовком `X-Pair-Poll-Token` — это bearer-секрет,
> а query-строка оседает в access-логах прокси и в APM-трейсах. Query-форма
> поддерживается и дальше, ради уже выпущенных сборок приложения.
Приложение опрашивает, пока бот не завершит pairing.

- **Ответ:** `{ "status": "pending" }` | `{ "status": "completed", "accessToken": string, "refreshToken": string, "expiresAt": datetime }` | `{ "status": "expired" }`
- **Ошибки:** 404 — `pollToken` неизвестен; 400 — `pollToken` не передан ни в query, ни в заголовке; 429 — лимит (60/мин на IP; приложение полит раз в 2 с = 30/мин, то есть двойной запас)
- `accessToken` — JWT на **Account** (claim `fatvpn_account_id`), в отличие от deep-link-пути (claim `fatvpn_token_id`). `refreshToken` — как в `/auth/token`.
- ⚠️ В ответе **нет** `accessTokenExpiresAt`/`subscriptionExpiresAt` — только `expiresAt`
  (срок подписки). См. оговорку в `/auth/token`.
- **Код одноразовый, и это теперь атомарно:** статус переводится в `Consumed` одним
  условным `UPDATE` внутри транзакции, вместе со вставкой refresh-токена. Проигравший
  гонку (повторный поллинг, дубль от сетевого стека) получает `{"status":"expired"}`, а
  не вторую 90-дневную сессию. Ветка «аккаунт исчез под завершённым кодом» тоже гасит
  код, чтобы приложение не поллило вечно.

### `POST /trial`
Выдать триал новому устройству (без ввода кода).

- **Запрос:** `{ "attestationToken": string, "platform": "ios" | "android" }`
- **Ответ:** `{ "accessToken": string, "refreshToken": string, "expiresAt": datetime }`
  (без `accessTokenExpiresAt`, см. оговорку в `/auth/token`)
- **Ошибки:** 400 — `attestationToken` пустой или неправдоподобной длины (**допустимо 16–512 символов**); 409 — триал этого устройства уже израсходован; 502 — не удалось создать подписку в Remnawave; 429 — лимит (**5/час на IP**)
- **Повторный вызов с тем же устройством — не всегда 409.** Пока триал ещё идёт,
  эндпоинт **переиздаёт сессию** (200): устройство, вышедшее из аккаунта и потерявшее
  refresh-токен, иначе осталось бы без доступа к своему же оплаченному времени. 409
  отдаётся, только когда триал уже истёк (или строка `Trial` указывает на несуществующий
  токен — наследие бэкфилла миграции `AddTokenIdToTrial`, такой случай пишется в лог).
- **Нижняя граница длины важна:** пустой `attestationToken` хешировался в `SHA256(salt)` —
  одну и ту же device-identity для всех, и второй звонящий получал сессию к чужому триалу.
- **Гонка двух одновременных вызовов** одного устройства больше не даёт 500 и не оставляет
  лишнего пользователя в панели: проигравший удаляет созданного им пользователя
  (`DELETE /api/users/{uuid}`) и переиздаёт сессию по триалу победителя.
- **Срок триала:** **2 дня** (`Trial:DurationDays` в `appsettings.json`; было 3, изменено на 2 по решению заказчика 2026-07-07).
- **Выдача подписки — на лету (2026-07-07):** `POST /trial` **создаёт нового пользователя в Remnawave** через `POST /api/users` (squad `Remnawave:TrialSquadUuid`, по умолчанию `Default-Squad`, `NO_RESET`, срок = now + `Trial:DurationDays`) и берёт его `shortUuid` как `remnawaveSubscriptionId`. Пул (`TrialSubscriptionSlots`) больше **не используется** — это масштабируется на любое число установок из стора без ручного пополнения. Старые эндпоинты `/internal/trial-pool` оставлены как legacy (не задействованы).
- **Анти-абуз (MVP, см. "Открытые вопросы"):**
  - `attestationToken` пока НЕ верифицируется через Play Integrity/App Attest — он просто солёно хешируется (`Trial:DeviceKeySalt`) и используется как ключ устройства в таблице `Devices` (409 при повторе).

### `GET /servers`
Список стран с вложенным списком реальных нод (адрес/порт для клиентского TCP-пинга).

- **Авторизация:** JWT Bearer (эндпоинт закрыт с pairing-релиза)
- **Ответ:** `[{ "country": string, "flag": string, "nodeCount": int, "nodes": [{ "id": string, "name": string, "address": string, "port": int, "usersOnline": int }] }]`
- **Фильтр:** возвращаются только ноды с `isConnected && !isDisabled` из `/api/nodes` (офлайн/выключенные скрыты).
- **⚠️ Почему в приложении меньше нод, чем в панели:** приложение показывает **пересечение**
  `/servers` (все подключённые ноды) с `/config` (ноды подписки), матч по адресу `host == node.address`
  (`app/lib/services/api_client.dart` `getUsableServers`). Нода видна, только если она одновременно
  подключена/включена И присутствует в подписке под тем же адресом. Диагностику расхождения
  (офлайн-ноды, Hysteria не в подписке) см. в `docs/app-bff-integration.md`.
- **Кеш:** ответ одинаков для всех пользователей, поэтому кешируется на BFF **45 с**
  (с single-flight — «стадо» одновременных запросов уходит в панель одним вызовом) и
  отдаётся с заголовком `Cache-Control: private, max-age=45`. Нода, ушедшая в офлайн,
  пропадает из списка в течение минуты.
- **Ошибки:** 401 — токен невалиден/сессия неизвестна; **402 — подписка истекла**; 502 — панель недоступна/ответила не-JSON; 429 — глобальный лимит

### `GET /config`
Конфиг подписки для текущего пользователя (по JWT). Проксирует ответ Remnawave, **дополняя его Hysteria-нодами** (см. ниже).

- **Ответ:** контент подписки Remnawave с оригинальным `Content-Type`
- **Примечание:** Remnawave на текущей инсталляции возвращает base64-кодированный список
  vless:// URI. Sing-box шаблон в панели не настроен — при необходимости JSON-формата
  нужно настроить шаблоны в Remnawave или добавить `?format=singbox` после конфигурации панели.
- **⚠️ Инъекция Hysteria (PoC, 2026-07-11):** Remnawave **не рендерит** наши Hysteria2-ноды
  (FR/US/FI «H2») ни в один формат подписки — они работают как Xray-hysteria-плагин, а не
  xray-core, и генератор подписки их пропускает. Поэтому `SubscriptionAugmenter`
  (`FatVpn.Bff.Infrastructure/Remnawave`) декодирует base64-подписку, достаёт `vlessUuid`
  пользователя прямо из его `vless://`-строк (он же — пароль для Hysteria2) и **дописывает**
  синтезированные `hysteria2://<uuid>@host:443?sni=host&alpn=h3#name` для этих хостов, затем
  кодирует обратно. Хосты задаются настройкой **`Remnawave:HysteriaHosts`** (дефолты —
  прежние FR/US/FI, params взяты из Happ/xray-json рендера панели); из `/api/hosts` их
  по-прежнему не тянем — это лишний round-trip на каждый `/config`. Инъекцию целиком
  выключает `Remnawave:AugmentHysteria=false`. Безопасный no-op, если контент не
  base64/нет vless-строки.
- **`subscriptionId` проверяется** перед походом в панель (4–64 символа, `A-Za-z0-9-_`) и
  URL-экранируется: значение приходит от бота, и `../api/users` раньше переадресовывал
  запрос на другой путь панели. Нарушение формата → 502.
- **Не кешируется** (в отличие от `/servers`): ответ персональный и несёт креденшелы.
- **Ошибки:** 401 — токен невалиден/сессия неизвестна; **402 — подписка истекла**; 502 — Remnawave недоступен/ответил не-JSON/таймаут 10 с

### `GET /me`
Статус подписки, срок действия.

- **Ответ:** `{ "status": "active" | "expired", "expiresAt": datetime, "subscriptionId": string?, "keyCode": string? }`
- ⚠️ **`status` бывает только `active` или `expired`** (`MeController`: `IsActive ? "active" : "expired"`).
  Отдельного `"trial"` эндпоинт **никогда не возвращал** — триал отличается от платной
  подписки только сроком. Приложение это и так учитывает (`AccountStatus.isActive`
  сравнивает с `'active'`), но документация обещала третье значение.
- `keyCode` — «Код для FatVPN App», который показывает бот (см. `/internal/*` ниже). Приложение показывает его как «Текущий ключ» для pairing-сессий, где код не вводился вручную; `null` для trial/legacy-сессий или если бот его не прислал. `subscriptionId` — Remnawave shortUuid (фолбэк, если `keyCode` нет).
- **Ошибки:** 401 — токен валиден, но сессия неизвестна (аккаунт/токен удалён) — как у `/servers` и `/config`

## Внутренние эндпоинты (только для тестового/прод Telegram-бота)

### `POST /internal/tokens`
Регистрация короткого токена ботом при нажатии «сменить ключ» (legacy deep-link-путь).

- **Авторизация:** секрет бота (заголовок, не JWT)
- **Запрос:** `{ "shortToken": string, "remnawaveSubscriptionId": string, "expiresAt": datetime }`
- **Ответ:** 201 Created — **всегда**, в том числе при обновлении уже известного ключа.
  По REST должно быть 200, но бот живёт вне репозитория и может проверять именно 201;
  ломать перевыпуск ключа ради этого не стали.
- Перевыпуск ключа **сбрасывает привязку к устройству** (`BoundDeviceKeyHash = null`),
  чтобы пользователь со сменённым/переустановленным телефоном мог активироваться заново.
- `expiresAt` нормализуется в UTC на входе (бот шлёт московское время; Npgsql не пишет
  `timestamptz` с ненулевым offset — раньше это давало 500 на каждой покупке ключа).

### `POST /internal/pair/complete`
Бот завершает pairing по коду: создаёт/обновляет Account и привязывает к нему код.

- **Авторизация:** секрет бота (`X-Bot-Secret`)
- **Запрос:** `{ "pairCode": string, "telegramUserId": int64, "subscriptionId": string, "expiresAt": datetime, "keyCode": string? }`
- `keyCode` (опционально) — «Код для FatVPN App»; сохраняется на Account и отдаётся в `/me`, чтобы приложение показывало тот же код, что и бот. Если не прислан — не перезаписывает уже сохранённый.
- **Ответ:** 200 OK
- **Ошибки:** 404 — код неизвестен/истёк; 409 — код уже использован

### `POST /internal/account/subscription`
Бот обновляет текущую подписку аккаунта при любом изменении активного ключа (создание/смена/продление). Upsert по `telegramUserId`. Именно это не даёт продлению/смене ключа рвать сессию приложения.

- **Авторизация:** секрет бота (`X-Bot-Secret`)
- **Запрос:** `{ "telegramUserId": int64, "subscriptionId": string, "expiresAt": datetime, "keyCode": string? }`
- `keyCode` (опционально) — «Код для FatVPN App». Слать при каждом изменении ключа (смена/продление), чтобы «Текущий ключ» в приложении оставался в синхроне с ботом. Если не прислан — сохранённое значение не затирается.
- **Ответ:** 200 OK

> Полное ТЗ по стороне бота — `docs/bot-pairing-spec.md`.

**Открытые вопросы:**
- Sing-box шаблоны в Remnawave — нужна настройка панели, чтобы `/config` отдавал JSON.
- Лимит устройств на ключ (у Sota — 1) — влияет на `/auth/token` и `/trial`.
- **⚠️ Абуз триала «удалил → скачал заново» (нужно реализовать перед стором).** Сейчас `attestationToken` — это случайный UUID в `flutter_secure_storage`. При удалении приложения хранилище стирается → при переустановке генерируется новый ключ → сервер видит «новое устройство» → **выдаёт ещё один триал**. Т.е. триал можно крутить бесконечно (удалил/поставил). Планы фикса:
  - **Стопгап (без гугл/эппл-аккаунтов): ANDROID_ID (SSAID)** как `attestationToken` вместо случайного UUID. Переживает переустановку (пока APK подписан тем же ключом), сбрасывается только factory reset → повтор даёт 409. Стабилен только на **release**-сборке (у debug ключ подписи может отличаться). Закрывает казуальный абуз, делается быстро.
  - **Правильно (для стора): Play Integrity API (Android) / App Attest (iOS)** — привязка к устройству+приложению, не обходится переустановкой и не подделывается. Требует Google Cloud service account и Apple-аккаунт. Это же закрывает и следующий пункт (верификацию `attestationToken`).
- Реальная верификация `attestationToken` (Play Integrity / App Attest) — не реализована, см. пункт выше и `POST /trial`.
- Выдача триала теперь **на лету** (создание Remnawave-юзера при `POST /trial`), пул `TrialSubscriptionSlots` больше не используется (legacy). Открытый вопрос по пулу снят.
