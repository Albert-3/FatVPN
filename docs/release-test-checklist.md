⚠️ **Бампать `app/pubspec.yaml` руками больше не нужно и бесполезно.** С 2026-07-28
`ios-release` вычисляет номер сам — `BUILD_NUMBER="$(git rev-list --count HEAD)"` и
передаёт его флагом `--build-number`, перекрывая pubspec (`codemagic.yaml`, шаг
«Build ipa»). Счётчик коммитов монотонен, так что забытый бамп больше не стоит сборки.
Из pubspec берётся только **имя** версии (`1.0.4`). Оба `Info.plist` (Runner и
PacketTunnel) читают `FLUTTER_BUILD_NUMBER` и получают уже подставленное значение.

### T-Android. На устройстве

> ⚠️ **Почему этот блок нельзя пропустить.** Статическая половина приёмки (T1–T3) зелёная,
> но всё, что переписано в доработках, живёт **за platform channel'ами**, куда хост-тесты
> не достают: нативный пинг через `VpnService.protect()`, секрет clash API в конфиге
> туннеля, событийное ожидание disconnect, foreground-уведомление, миграция secure
> storage, исключение ABI. Ни один из пунктов ниже не проверен.

- [ ] **T21. Подключение как таковое.** Изменились **и механизм пинга** (нативный
      `pingServerOutsideTunnel` написан с нуля), **и сам конфиг** (в `experimental.clash_api`
      добавился `secret`). Проверить: туннель поднимается, трафик идёт, выбор «лучшего
      сервера» отрабатывает за разумное время. ⚠️ Отдельно засечь время от нажатия
      «Подключить» до `Tunnel established` при нескольких недоступных нодах в пуле:
      первая версия параллельных пингов была **медленнее** последовательной (находка N1),
      и регрессия воспроизводится только на устройстве.
- [ ] **T22. Авто-переключение.** `waitForDisconnected` стал событийным вместо
      busy-wait, а загрузка нод снова читается «живой» (`getServers(force: true)`,
      находка N2). Проверить, что переключение происходит, сессия не рвётся для
      пользователя, таймер не обнуляется и «прыжков» по кругу нет (см. E1–E4).

- [ ] **T6. Холодный старт после kill процесса во время рефреша** (§2.1 — главный
      сценарий потери платной подписки). Приложение безусловно рефрешит сессию на
      старте, поэтому: запустить, и **сразу** (в пределах секунды, пока идёт
      `/auth/refresh`) убить процесс — `adb shell am force-stop com.fatvpn.fatvpn_app`.
      Запустить снова. Повторить **5 раз подряд**.
      Ожидание: каждый раз приложение открывается **в своей сессии**. Выброс на онбординг
      или `signOut` в логе = ротированный токен не успел лечь на диск, баг не закрыт.
- [ ] **T7. Sign-out при активном туннеле** (§2.4). Подключиться, затем Настройки →
      выйти из аккаунта. Ожидание: **туннель опускается** — иконка VPN уходит из
      статус-бара, foreground-нотификация исчезает, `tun0` разобран. Онбординг при
      поднятом туннеле = дефект. Проверить оба пути: ручной выход и автоматический по 401.
- [ ] **T8. Смена сервера** при поднятом туннеле — коннект идёт к **выбранной** стране
      (регресс-проверка находки №1), карточка локации показывает её же.
- [ ] **T9. Clash API недоступен чужому приложению** (§1.6). При поднятом туннеле, **без**
      `adb forward`, из shell-контекста (он для приложения чужой):

- [ ] **T10. Wi-Fi ↔ LTE под нагрузкой.** Начать крупную загрузку через туннель и

- [ ] **T11. `allowBackup`** (§1.4): в манифесте `android:allowBackup="false"` (или

- [ ] **T24. После disconnect/logout на диске не осталось конфига с креденшелами**
      (2.1, 1.6).
      **Как выгрузить контейнеры** (Mac, `xcrun devicectl`, UDID берётся из
      `xcrun devicectl list devices`):
      ```
      xcrun devicectl device copy from --device <UDID> \
        --domain-type appDataContainer --domain-identifier com.fatvpn.fatvpnApp \
        --source "Library/Application Support/signbox" --destination ./out-app
      xcrun devicectl device copy from --device <UDID> \
        --domain-type appGroupDataContainer --domain-identifier group.com.fatvpn.fatvpnApp \
        --source . --destination ./out-group
      ```
      Запасной путь без `devicectl`: Xcode → Window → Devices and Simulators →
      приложение → шестерёнка → «Download Container…». Он даёт контейнер **приложения**
      (`active-config.json`), но **не** App Group — то есть `start_options.plist` так не
      увидеть.
      **Что искать:**
      | Файл | Где | Ссылка |
      |---|---|---|
      | `active-config.json` | контейнер приложения, `Library/Application Support/signbox/` | `SingboxMmPlugin.swift:363,390` |
      | `start_options.plist` | корень App Group | `PacketTunnelProvider.swift:12,187-190` |
      | `diagnostics.txt` | корень App Group | `PacketTunnelProvider.swift:130` |
      | `Caches/stderr.log` | App Group | `PacketTunnelProvider.swift:124,158` |
      **Порядок:** подключиться → выгрузить (файлы должны быть, это норма) →
      отключиться **и выйти из аккаунта** → выгрузить снова → искать:
      ```
      grep -REn "[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-" out-app out-group | head
      grep -REn "password|private_key|short_id|\"auth\"|pbk=|sid=" out-app out-group | head
      ```
      (`start_options.plist` — binary plist, перед grep прогнать через
      `plutil -convert xml1`.)
      **Ожидание:** после logout либо файлов нет, либо в них нет ни UUID, ни паролей,
      ни приватных ключей, ни адресов нод.
      **Провал:** нашлось хоть что-то — подписка пользователя переживает выход из
      аккаунта на диске. Дополнительная проверка бэкапа (вторая половина 2.1): сделать
      **незашифрованный** локальный бэкап через Finder и поискать те же строки в нём;
      если файлы туда попали — не выставлен `isExcludedFromBackup`, и компрометация
      бэкапа = компрометация подписки.

- [ ] **T25. Support bundle не содержит UUID / паролей / доменов** (2.4).
      **Как:** поднять туннель, **специально** открыть в Safari «маркерный» домен,
      который больше нигде не встречается (например `marker-<случайная строка>.example`
      — резолв провалится, но в лог он попадёт), походить ещё по паре сайтов, затем
      Настройки → собрать support bundle → сохранить в «Файлы» и **прочитать глазами**,
      после чего прогнать grep.
      **Ожидание:** в бандле нет ни `vless://`/`trojan://`/`hysteria2://`, ни UUID, ни
      `password=`/`pbk=`/`sid=`/`auth=`, ни адресов нод вида `ip:port`, и **нет
      маркерного домена**.
      **Провал:** найдено что угодно из перечисленного. ⚠️ Маркерный домен — самая
      важная часть: он доказывает, что в бандл не уезжает история посещений. На iOS
      туда кладётся хвост `stderr.log` (6000 байт) и `diagnostics.txt` целиком
      (`SingboxMmPlugin.swift:765-792`) — именно они несут домены. Нативные
      санитайзеры с 2026-07-28 есть в обоих местах (`PacketTunnelProvider.redactSecrets`
      чистит текст **до** записи в `diagnostics.txt`, `SingboxMmPlugin.redactSecrets` —
      хвост `stderr.log`), но **от домена они не защищают**: домен без пароля не
      выглядит секретом ни для одного regex. Единственное, что его убирает, —
      запрет `logLevel: debug` в release (`singbox_config_builder.dart`). Поэтому
      маркерный домен и есть настоящий предмет проверки, а не UUID.

#### T-iOS, вторая волна (добавлено 2026-07-28 по итогам вычитки кода)

> **Зачем.** Первые восемь пунктов (T12–T16, T23–T25) закрывают находки, которые
> аудит назвал **критическими и high**. Но ремедиация изменила поведение ещё в
> четырнадцати местах, и ни одно из них не имело пункта приёмки — включая те, что
> сам `docs/improvement-plan-ios.md` прямым текстом называет непроверяемыми без
> устройства (MTU, `system`-стек, смена сервера, счётчики трафика). Пункт без
> проверки — это находка, закрытая на словах.

- [ ] **T26. Смена сервера при живом туннеле** (1.10).
      **Как:** подключиться, сменить локацию 10 раз подряд; три из них — во время
      активной загрузки крупного файла. Засекать время до «Подключено».
      **Ожидание:** срабатывает **каждая** смена; прежней «магической» паузы 0.6 с
      нет (её заменил `awaitDisconnected` по событию).
      **Провал:** хоть одна смена молча не сработала (`startVPNTunnel` в состоянии
      `.disconnecting` ничего не делает) — или карточка показывает одну страну, а
      выходной IP принадлежит другой.

- [ ] **T27. Счётчики трафика** (1.12) — **полностью новое поведение**: до правки
      `uplinkBytes`/`downlinkBytes` никогда не инкрементировались, на iOS в UI всегда
      был ноль. Это не «восстановили», а «сделали впервые».
      **Как:** открыть экран статистики при живом туннеле, скачать файл известного
      размера (50–100 МБ). Затем свернуть приложение на 10 минут и вернуться.
      **Ожидание:** числа растут, порядок величины сходится с размером файла; после
      возврата из фона счётчик снова живой.
      **Провал:** нули (команда `stats` не доходит до расширения), цифры, не связанные
      с трафиком, — или счётчик, не ожившый после фона (таймер погашен и не поднят).

- [ ] **T28. Скорость и стабильность на `system`-стеке и MTU 1280** (3.2, 3.4) —
      **самая рискованная правка документа**: меняется путь обработки каждого пакета.
      **Как:** speedtest ×3 на Wi-Fi и ×3 на LTE, сравнить с цифрами build 18
      (gvisor + MTU 1100). Затем сессия 2+ часа с периодической нагрузкой.
      **Ожидание:** скорость не ниже прежней (ожидается выше), обрывов нет.
      **Провал:** сайты открываются частично или виснут на крупных ответах — это
      классический признак неверного MTU; либо скорость упала против gvisor.

- [ ] **T29. Таймауты старта** (1.4).
      **Как:** подключиться к заведомо недоступной ноде; отдельно — попробовать
      подключиться при активном чужом VPN-профиле.
      **Ожидание:** внятная ошибка не позже ~40 с (`startupDeadline`), тоггл
      возвращается в «Отключено».
      **Провал:** «Подключение» висит до 60-секундного дедлайна Dart или бесконечно —
      значит `runBlocking` снова блокируется без таймаута.

- [ ] **T30. sleep/wake после ночи** (1.13).
      **Как:** подключиться, оставить iPhone заблокированным 6+ часов, утром **сразу**
      открыть свежий URL мимо кеша.
      **Ожидание:** трафик идёт без ручного переподключения.
      **Провал:** «Подключено», но трафика нет до тогла — ядро осталось на паузе,
      `wake()` не пришёл. В логе `PacketTunnel` при этом **не должно** быть цепочки
      `attemptRecovery`: watchdog не имеет права «лечить» паузу перестройкой ядра.

- [ ] **T31. Clash API требует секрет и только loopback** (2.2, 2.3).
      **Как:** при живом туннеле с Mac в той же сети — `curl -m 3
      http://<IP-телефона>:16756/configs`. Локально — убедиться в логе расширения, что
      запросы идут с `Authorization: Bearer`.
      **Ожидание:** снаружи соединение не устанавливается.
      **Провал:** `/configs` ответил чем угодно, кроме отказа. ⚠️ Порт **не**
      рандомизирован (16756 захардкожен) — сам факт работающего VPN снаружи виден, это
      известный незакрытый пункт 2.2, а не провал теста.

- [ ] **T32. Первый коннект без `cache_file`** (3.3).
      **Как:** засечь время от «Подключить» до первой открытой страницы на холодном
      старте, 5 раз.
      **Ожидание:** деградация в пределах секунды-двух против build 18.
      **Провал:** заметно дольше — тогда выключение `cache_file`/`store_fakeip` на iOS
      обошлось дороже сэкономленной памяти, и решение надо пересматривать.

- [ ] **T33. Батарея и интервалы watchdog'а** (3.5, 3.6, 3.7).
      **Как:** ночь под VPN без нагрузки; утром Настройки → Аккумулятор → расход
      FatVPN, и в Console.app посчитать циклы проверки.
      **Ожидание:** ~20 циклов за ночь (180 с), на LTE / в Low Power Mode — ~12
      (300 с). Было бы ~480 при старом интервале 60 с.
      **Провал:** интервал не адаптируется, либо расход батареи не ниже build 18.

- [ ] **T34. Kill-switch действительно блокирует** (1.3).
      **Как:** включить «Блокировать трафик без VPN», подключиться, убить расширение
      (способ (б) из T23).
      **Ожидание:** пока туннель не поднялся — интернета **нет вообще**.
      **Провал:** `ip-api.com` отдаёт реальный IP оператора, то есть kill-switch
      называется kill-switch, но трафик идёт в обход.

- [ ] **T35. Fallback при недоступном App Group** (1.9).
      **Как:** применимо, если шаг `codesign` в CI покажет отсутствие capability — не
      чинить сразу, а сначала прогнать сборку на устройстве.
      **Ожидание:** туннель **поднимается**, а `getLastError` отдаёт
      `APP_GROUP_UNAVAILABLE: <id>` — то есть диагностика недоступна, а VPN работает.
      **Провал:** крэш расширения (значит, где-то остался `fatalError`) или крэш-луп с
      экспоненциальным backoff от iOS.

- [ ] **T36. Долгая сессия под гонками** (1.5, 1.11, 1.15).
      **Как:** 2 часа непрерывно: смены сервера, авто-переключение, уходы в фон, смены
      сети, открытый экран статистики.
      **Ожидание:** ни одного отчёта о падении `PacketTunnel` в Настройки →
      Конфиденциальность → Аналитика; память расширения не растёт монотонно.
      **Провал:** падение расширения (гонка на `tunnelOptions`) или монотонный рост
      памяти (утёкшие `NWConnection` из перебора нод).

## 2d. Защита от трекинга (добавлено 2026-08-02)

Тумблер «Защита от трекинга» в Настройки → Настройки подключения. Заказчик
просил «блокировку рекламы»; функция делает именно это, но называется по
трекингу — Play снимает с публикации приложения, вмешивающиеся в показ чужой
рекламы (`docs/store-compliance.md` §3.1a). Список доменов вшит в приложение
(`app/lib/services/tracker_block_list.dart`), режется правилом
`domain_suffix → block` внутри sing-box. Покрыто 16 host-тестами
(`app/test/tracker_protection_test.dart`) и 7 на уровне плагина
(`tracker_block_rule_order_test.dart`).

### Прогон на эмуляторе, 2026-08-02

Pixel 7 / API 35 (Google Play образ), debug-сборка от `ead085e`, живая сессия
(триал с прод-BFF), туннель на реальные ноды. **Это эмулятор, не телефон:**
не проверены отзыв разрешения VPN системой, поведение при смене сети, работа
после долгого сна и всё, что делает Android на настоящем устройстве, — но
маршрутизация внутри sing-box здесь настоящая, потому что смотрели не UI, а
`files/singbox/active-config.json` живого туннеля (`adb shell run-as`) и
поведение браузера через него.

Итог: **TA1, TA2, TA3, TA4, TA8, TA9, TA10, TA11, TA12, TA13 прошли**, TA5 и
TA7 прошли частично (см. ниже). Найдено три дефекта, два починены здесь же:

1. ⛔ **`yabs.yandex.ru` не был в списке** — а это тот хост, с которого Яндекс
   Директ реально отдаёт свои блоки. С включённой защитой `ya.ru` всё равно
   рисовал рекламный баннер: `an.yandex.ru` в списке был, а он закрывает
   старый путь доставки, не текущий. То есть на единственной странице, на
   которой русский пользователь скорее всего и проверит тумблер, тумблер
   выглядел неработающим. Добавлен; после этого баннер на `ya.ru` пропал, а
   с выключенной защитой вернулся.
2. ⛔ **`AppLogger.e` падал на каждой ошибке** (починено, регрессионный тест
   `app/test/app_logger_error_flush_test.dart`). `IOSink.flush()` связывает
   sink до завершения своего future, запись в связанный sink кидает
   `Bad state: StreamSink is bound to a stream`. `e()` пишет две строки —
   сообщение и стек, — и первая запускает flush по ошибке, так что вторая
   всегда попадала в это окно. `main()` зовёт `log.e` из `FlutterError.onError`,
   поэтому бросок происходил **внутри обработчика ошибок**: сама ошибка не
   доходила ни до консоли, ни до файла, ни до саппорт-бандла, а кадр, в
   котором она возникла, отбрасывался. Наблюдалось как **пустой экран
   раздельного туннелирования** — список приложений не рисовался вообще, и в
   логе не было ни слова почему. Под ним пряталась безобидная debug-ассерта
   `ListTile background color or ink splashes may be invisible`.
3. ⚠️ **`ListTile` без Material-предка** в списке приложений (та самая ассерта,
   13 раз за отрисовку). В release не срабатывает; после починки логгера ни на
   что не влияет, но чернильные всплески в списке могут быть невидимы.
   Не трогали.

Чего прогон **не** закрыл: рекламу вне Яндекса (баннеры западных сетей на
эмуляторе не смотрели), TA5 целиком (боты, карты, Ozon/WB, мессенджеры —
проверялись только `ya.ru`, `api.ipify.org` и сам список серверов), и TA7 в
строгой формулировке (тумблер щёлкали при выключенном туннеле несколько раз,
падений и исключений в logcat нет, но «настройка применена при следующем
подключении» отдельно не сверялась — она сверена в других пунктах).

**Защита и раздельное туннелирование взаимоисключающие** (решение заказчика,
2026-08-02). Включил одно — второе выключается само и **возвращается**, когда
первое выключишь; правила при этом никуда не деваются. Так убран вопрос, на
который иначе пришлось бы отвечать: правило блокировки матчится раньше правил
обхода, то есть с обоими включёнными домен из списка обхода всё равно мог бы
блокироваться — список обхода тихо перестал бы значить то, что значил во всех
выпущенных сборках.

Почему список вшит, а не качается: удалённый `rule_set` в sing-box — это
зависимость **старта роутера**. Скачивание идёт до того, как есть туннель, из
сети, которая и является причиной, по которой пользователь поставил VPN; а на

подключаться». Цена решения: список меняется только вместе со сборкой.

## 2f. Пиннинг сертификата (добавлено 2026-08-02)

Приложение больше не доверяет хранилищу устройства при разговоре с BFF: доверенных
корней ровно четыре, все — ISRG (`app/lib/config/ca_pins.dart`). Что уже проверено
**с этой машины** и переписывать руками не нужно: живой `api.fatklyuchi.space`
отвечает 200 под этим набором корней (тем же стеком Dart/BoringSSL, что и в
приложении), а `google.com` под ним же отваливается `HandshakeException` — то есть
системные корни действительно выключены, а не «выключены в коде».

⚠️ **Проверка «с этой машины» ничего не говорит про iOS, и это выяснилось дорого.**
Dart проверяет сертификаты BoringSSL'ем на Android, Linux и Windows, но на всём,
что от Apple, отдаёт проверку **SecTrust** (`runtime/bin/security_context_macos.cc`,
он же компилируется под iOS): наш набор корней приходит туда как *anchors*, а
`SecTrustSetAnchorCertificatesOnly(!trust_builtin)` выключает системные — то есть
пин на iOS действительно пинит, но решает про сертификат **политика Apple**, а не
наш код. Первое подтверждение пришло из CI 2026-08-03: `flutter test` на
macOS-раннере Codemagic уронил сборку iOS на контрольном тесте
`ca_pinning_test.dart`, зелёном на Windows во всех прогонах. Виновата была
фикстура (100 лет жизни и без `extendedKeyUsage=serverAuth` — Apple применяет свои
требования и к приватным CA), а не приложение; перевыпущена в тот же день, см.
`app/test/fixtures/tls/README.md`. Практический вывод для TA17: **на iOS
проверять обязательно отдельно**, «на Windows проходит» здесь не аргумент.

Ниже — то, чего с машины не видно. **TA17 важнее остальных вместе взятых:** он
отличает работающий пиннинг от кирпича, и до него ни одну сборку с этой правкой
раздавать нельзя.

- [ ] **TA17. Приложение вообще работает.** Обычный прогон на устройстве: вход,
      список серверов, подключение, `/me`. **Ожидание:** как раньше. **Провал:**
      всё сетевое молчит, а в журнале — `Rejected the certificate offered for
      api.fatklyuchi.space:443`. Это значит, что цепочка сервера больше не сходится
      к нашим корням, и лечится **новой сборкой**, а не настройкой: удалённого
      выключателя у пина нет. Проверять на **обеих** платформах — доверенное
      хранилище у них разное.
- [ ] **TA18. Перехват действительно не проходит.** Телефон за прокси-перехватчиком
      (mitmproxy / Charles) с установленным в систему его корнем; на iOS —

- [ ] **TA19. Виджет и фоновый путь тоже пинятся.** Нажать кнопку виджета на

## 4. Находки прогона 2026-07-27 (Android, эмулятор)

### 🔴 №1 — БЛОКЕР: смена локации при включённом VPN не применяется — **ИСПРАВЛЕНО**

**Симптом.** VPN подключён к TR. Пользователь выбирает DE в «Выборе локации» → приложение рвёт
туннель и поднимает его **снова на TR**. Воспроизведено 2 из 2 раз; при **выключенном** VPN тот же
выбор работает правильно (лог: `Connecting to node "ger_1cent"`).

```
02:21:30  Connecting to node "turk_4vps"   ← выбран DE, VPN был включён
02:26:47  Connecting to node "turk_4vps"   ← выбран DE, VPN был включён
02:32:17  Connecting to node "ger_1cent"   ← выбран DE, VPN был выключен ✅
```

**Причина** (`app/lib/screens/home_screen.dart:131`, следствие `023c425`): `_handleVpnChange`
подтягивает карточку локации за фактически подключённой нодой —

```dart
final node = _vpn.connectedNode;
if (node != null && country.country != _selectedServer?.country) {
  _selectedServer = country;   // затирает выбор пользователя
}
```

а `_openLocationPicker` после записи выбора вызывает `_switchOff()` → `disconnect()`, которая
обнуляет `_connectedNode` **только после** `await _vpn.stop()` (`vpn_controller.dart:852`). Пока
туннель разбирается, каждое событие состояния прилетает со старой нодой, и `_selectedServer`
откатывается с DE обратно на TR — а `_connectCurrentSelection()` читает уже откатанное значение.

**Почему блокер.** Это же ломает **F3** — уход с мёртвой ноды вручную, ровно тот сценарий, ради
которого делался кэш подписки (`18a3386`). Пользователь на неработающем сервере не сможет уйти.

**Фикс (сделан, оба слоя):**
1. `vpn_controller.dart` — `disconnect()` обнуляет `_connectedNode` **до** `await _vpn.stop()`, а не
   после. Пока туннель разбирается, никто больше не получает имя ноды, которую уже покидают.
2. `home_screen.dart` — `_handleVpnChange` следует за туннелем только в режиме «Лучший сервер»
   (`_serverExplicitlySelected == false`). В режиме явно выбранной страны выбор пользователя — это
   инструкция, а не отображение, и перезаписывать её нечем: пул авто-переключения и так ограничен
   нодами этой страны.

**Проверено после фикса:** выбор DE при активном туннеле → `Connecting to node "ger_1cent"`,
карточка показывает DE, вся операция 1.6 с (было: возврат на исходную ноду, 2/2 раза).

### 🔴 №6 — смена локации висела 2 минуты: у авторизованных запросов не было таймаута — **ИСПРАВЛЕНО**

Всплыло сразу после фикса №1. Лог первого ретеста:

```
02:55:51  Disconnecting tunnel (endSession=false)
02:55:51  GET /config
02:58:07  GET /config unreachable (Connection timed out) — reusing the last known subscription
02:58:07  Connecting to node "ger_1cent"
```

**2 минуты 16 секунд** между запросом и вердиктом — всё это время UI показывал «Подключение…».

**Причина.** `ApiClient._authedGet` — единственный метод без `.timeout()` (у auth-методов стоит
10–15 с), а через него идут `/servers`, `/me`, `/config`. Раньше это было безобидно: запросы шли
мимо туннеля. После `58f16af` они идут внутрь, и запрос, выпущенный в умирающий туннель, наследует
системный TCP-таймаут.

**Фикс:** `_requestTimeout = 15 s` на обе ветки `_authedGet` (основную и retry после 401), плюс
`TimeoutException` добавлен в `VpnController._isNetworkError`, чтобы пользователю показывалось
человеческое «не удалось связаться с сервером», а не сырой текст исключения. Таймаут — это то, что
позволяет `getConfig` быстро уйти в кэш подписки (`18a3386`) и продолжить реконнект.

**Проверено:** та же операция после фикса — **1.6 с** (сокет упал сразу, а 15 с остаются потолком
худшего случая).

### 🔴 №7 — БЛОКЕР: добавление домена в сплит роняет экран красным экраном — **ИСПРАВЛЕНО**

**Симптом.** Настройки → Раздельное туннелирование → Домены/IP → «Добавить домен или IP» → `ya.ru`
→ «Добавить». Экран целиком заменяется красным экраном ошибки Flutter, **и домен не сохраняется**
(после перезапуска в списке снова 4 домена вместо 5). Воспроизведено на первой же попытке.

```
04:10:48  [ERROR] FlutterError: A TextEditingController was used after being disposed.
04:10:48  #4  _AnimatedState.didUpdateWidget (transitions.dart:119:25)
04:10:49  [ERROR] FlutterError: Failed assertion: line 6268 pos 12: '_dependents.isEmpty': is not true.
04:10:49  #2  InheritedElement.debugDeactivated (framework.dart:6268:12)
```

**Причина** (`app/lib/screens/split_tunnel_hosts_screen.dart:128`): контроллер создавался локально в
`_showAddDialog` и освобождался сразу после `await showDialog(...)`. Но future от `showDialog`
завершается в момент `Navigator.pop`, **пока диалог ещё играет анимацию закрытия**, и его `TextField`
всё ещё подписан на этот контроллер. Обращение к освобождённому `ChangeNotifier` валит ассерт, дерево
виджетов рассыпается — и вместе с ним теряется только что добавленный домен.

**Почему блокер.** Ломается основной способ настроить обход: пользователь не может добавить свой
домен. В release-сборке красного экрана не будет (ассерты выключены), но обращение к освобождённому
контроллеру остаётся, а потеря домена — тем более.

**Фикс:** контроллер стал полем `_HostBypassEditorState` (`_hostController`), освобождается в
`State.dispose()`, а перед показом диалога просто чистится (`..clear()`).

**Проверено после фикса:** `ya.ru` добавляется, красного экрана нет, в логе ни одной ошибки,
в списке 5 доменов, значение переживает перезапуск приложения.

### 🟠 №8 — кнопка «Cancel» в диалоге не переведена — **ИСПРАВЛЕНО**

В диалоге добавления домена при RU-локали кнопка называлась `Cancel`, хотя соседняя — «Добавить».
Причина: `split_tunnel_hosts_screen.dart:111` брал текст из
`MaterialLocalizations.of(context).cancelButtonLabel`, а приложение **не подключает**
`flutter_localizations` (делегатов нет нигде в `lib/`), поэтому `MaterialLocalizations` отдаёт
английские дефолты независимо от выбранного языка.

**Фикс:** добавлена своя строка `cancel` в `Strings` (EN `Cancel` / RU `Отмена`), диалог использует
`s.cancel`. **Проверено:** в RU-локали кнопка теперь «Отмена».

> ⚠️ Тот же класс проблемы может всплыть в любом другом месте, где берутся строки Material
> (тексты выбора даты/времени, `Paste`/`Select all` в контекстном меню полей ввода). Отдельная
> задача: либо подключить `flutter_localizations` с RU, либо продолжать перекрывать строки вручную.

## 4a. Проверено и оказалось НЕ дефектом (чтобы не искать заново)

- **`Session refreshed (token rotated)` на каждое возвращение в приложение — так задумано.**
  Настораживало, что за 8 минут refresh случился 4 раза при 30-минутном access-токене. Это
  `AuthController.refreshOnResume()` («чтобы подхватить продление/истечение подписки без действий
  пользователя»), а лишние срабатывания давал сам ANR-диалог: его закрытие — это тоже resume.
  Признак того, что refresh идёт **не** от 401: в логе нет строки `GET … → 401, refreshing`.

- **Зависание приложения на «старом» эмуляторе — окружение, не код.** На эмуляторе с uptime 14.7 ч
  приложение получило ANR (`Input dispatching timed out … Waited 5037ms for FocusEvent`) и залипло
  насмерть: Dart-изолят при этом жил (таймер сессии продолжал идти), а Android main thread не
  потреблял события ввода. Против версии «баг в приложении» говорят замеры: `Load: 7.66`,
  **903 major page faults** за окно ANR, 2.2 ГБ из 2.5 ГБ занятой памяти и 517 МБ свопа
  (`pswpout` 2.8 млн страниц), а «Skipped 151 frames» и `SurfaceSyncGroup: Failed to receive
  transaction ready` относятся к PID 601/835 (`system_server`/`systemui`), а не к приложению —
  тормозил весь эмулятор. После перезагрузки эмулятора ни ANR, ни залипания не повторились.
  ⚠️ Совсем не закрывает I1: **проверять на реальном телефоне.**
