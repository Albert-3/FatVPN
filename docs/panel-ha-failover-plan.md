## 0. Почему упало всё, если упал один сервер

Панель Remnawave — не «админка». Это единственный владелец состояния всей системы:
в её Postgres лежат пользователи, подписки, ключи, сквады, ноды, счётчики трафика.
К ней в рантайме обращаются все остальные части:

```
                    ┌─────────────────────────────┐
                    │  Сервер панели (ЕДИНСТВЕННЫЙ)│
                    │  z.fatvdsnvv.space           │
                    │  Remnawave + Postgres        │
                    └──────┬──────────┬───────────┘
             REST API      │          │  управление нодами (:2222)
       ┌───────────────────┤          └──────────────┐
       │                   │                         │
┌──────┴──────┐    ┌───────┴────────┐        ┌───────┴───────┐
│ BFF          │    │ sub-страница   │        │ VPN-ноды      │
│ 87.121.221.229│   │ sub.fatklyuchi │        │ (N штук)      │
│ /config,     │    │ .space         │        │ VLESS/Hysteria│
│ /servers, /me│    │ (Yandex CDN →  │        │               │
└──────┬───────┘    │  origin=панель)│        └───────────────┘
       │            └────────────────┘
┌──────┴───────┐
│ Приложение +  │        Бот ──► BFF ──► панель (та же цепочка)
│ Telegram-бот  │
└───────────────┘
```

Что происходит при отказе панели, по компонентам:

| Компонент | Поведение при мёртвой панели |
|---|---|
| VPN-ноды | **Продолжают работать** на последнем полученном конфиге. Но: новый пользователь на ноду не попадёт, отключённый не отключится, а нода, перезапустившаяся в этот момент, останется без конфига |
| BFF `/config`, `/servers` | 502 (панель — upstream, `Remnawave__BaseUrl: https://z.fatvdsnvv.space`) → приложение не может подключиться и не видит серверов |
| BFF `/trial`, пейринг | Мертвы — создание пользователя и резолв подписки идут в панель |
| Бот (выдача/продление ключей) | Мёртв — вся работа с ключами идёт через панель |
| sub.fatklyuchi.space | Мертва — origin Yandex CDN смотрит на панель |
| Уже подключённые клиенты | Работают, пока не порвётся сессия и не понадобится свежий конфиг |

Отсюда два вывода, определяющие весь план:

1. **Реальная катастрофа вчера была не простоем, а риском потери данных.** Если бы
   сервер не вернулся, база клиентов исчезла бы безвозвратно — бэкапов нет. Поэтому
   этап 1 этого плана — бэкапы, а не резервные серверы: он закрывает худший сценарий
   и делается за день.
2. **Резервировать только панель недостаточно.** BFF (`87.121.221.229`) — точно такой
   же единственный сервер без бэкапов, и его отказ кладёт приложение у всех
   пользователей независимо от числа панелей. Это за рамками поставленной задачи,
   но зафиксировано в §11 — закрыть одну дверь из двух не считается.

## 1. Почему «три работающих панели» невозможны, и что возможно вместо них

У Remnawave нет кластерного режима. Две одновременно **активные** панели — это два
независимых Postgres, в которых состояние расходится с первой же операции: ключ
выдан в одной базе, продление записано в другой, счётчики трафика различаются
навсегда. Обратной процедуры слияния не существует.

Поэтому «три сервера» реализуются единственным корректным способом:

**Active / passive: один активный + два горячих резерва.**

- Панель (веб + API) запущена **только на активном** сервере.
- Postgres работает на всех трёх: primary на активном, два standby непрерывно
  догоняют его потоковой репликацией (отставание — секунды).
- При отказе активного: трафик переводится на резерв (Cloudflare Load Balancer,
  автоматически), standby промоутится в primary и на нём запускается панель
  (полуавтоматически, см. §7 — и это осознанное решение, а не недоделка).

### 1.1 Отвергнутые альтернативы — чтобы к ним не возвращаться

| Вариант | Почему нет |
|---|---|
| Active/active (3 живых панели) | Нет кластера → расходящиеся базы, несводимо. Не «сложно», а «нельзя» |
| keepalived / плавающий IP | Требует одного провайдера (floating IP не переезжает между хостерами) → отказ ДЦ или блокировка провайдера снимает все три сервера разом. Это воспроизведение вчерашней аварии за тройную цену |
| Периодический rsync/дамп на резерв вместо репликации | Резерв со «вчерашним» состоянием: всё, что куплено/продлено после последнего дампа, исчезает при переключении. Дампы остаются, но как слой бэкапа, не как механизм HA |
| Полный автопромоушен БД со своим скриптом | Split-brain: сеть между A и наблюдателем моргнула → поднялись два primary → расхождение хуже простоя. Автопромоушен возможен только с кворумом (Patroni/repmgr) — это этап 2, после того как базовая схема переживёт учения (§7.3) |

### 1.2 Целевая схема

```
                Cloudflare Load Balancer  (z.fatvdsnvv.space, DNS-only, TTL 30-60с)
                health-check GET / каждые 15с из нескольких регионов
                        │
        приоритет 1 ────┼──── приоритет 2 ──────── приоритет 3
        ┌───────────────┴──┐  ┌──────────────────┐  ┌──────────────────┐
        │ Сервер A (акт.)   │  │ Сервер B (резерв)│  │ Сервер C (резерв)│
        │ провайдер 1       │  │ провайдер 2      │  │ провайдер 3      │
        │ Remnawave: RUN    │  │ Remnawave: STOP  │  │ Remnawave: STOP  │
        │ Postgres: primary │  │ Postgres: standby│  │ Postgres: standby│
        └────────┬──────────┘  └────────┬─────────┘  └────────┬─────────┘
                 │      WireGuard-меш (10.77.0.0/24)          │
                 └────────── streaming replication ───────────┘
                             A → B  и  A → C

        Ноды: firewall 2222/tcp открыт для ВСЕХ ТРЁХ публичных IP заранее
```

Три сервера — **у трёх разных провайдеров** (или минимум у двух), в Европе, близко
по RTT. Одна локация дала бы приватную сеть и мгновенный floating IP, но общий
отказ ДЦ снимает все три; DNS-переключение за 30–60 секунд — приемлемая цена за
независимость. Репликация между провайдерами идёт по открытому интернету → только
через WireGuard.

Требования к каждому серверу: 2–4 vCPU, 4–8 ГБ RAM, 60+ ГБ NVMe, Ubuntu 22.04/24.04.
Панель нетребовательна; диск должен вмещать базу с запасом ×4 (WAL + бэкапы).
Ориентир цены: €8–20/мес за сервер.

## 2. Этап 1 — бэкапы. Делается первым, до покупки серверов

Единственная мера, закрывающая сценарий «сервер не вернулся», который уже случился.
Всё остальное в этом документе без неё — надстройка над пустотой.

### 2.1 Что бэкапим

| Что | Зачем |
|---|---|
| `pg_dump` базы панели (контейнер `remnawave-db`) | Всё состояние: пользователи, ключи, подписки, ноды |
| `/opt/remnawave/.env` (или где лежит стек панели) | **Критично:** `APP_SECRET` (panel v3+; для v2 — `JWT_AUTH_SECRET` + `JWT_API_TOKENS_SECRET`). Восстановленная база с чужим секретом отдаёт 403 на логин и не аутентифицируется — база есть, войти нельзя |
| `docker-compose.yml` панели и всё рядом (конфиги Xray, кастомные шаблоны) | Чтобы восстановление было «развернуть архив», а не «вспомнить, как было настроено» |

### 2.2 Куда и как

Два независимых назначения — хранилище может быть недоступно ровно тогда, когда
нужен бэкап:

1. **S3-совместимое хранилище** (Backblaze B2 / Wasabi / Selectel S3 — что угодно
   **не у тех же провайдеров**, где стоят серверы) через `rclone`. Retention: 24
   почасовых, 30 суточных.
2. **Telegram** — документом в приватный канал (`sendDocument`, лимит 50 МБ — дамп
   в `gzip -9` в него влезает с большим запасом; когда перестанет влезать, в
   Telegram остаётся только суточный, почасовые — в S3).

Скрипт `/opt/remnawave/backup.sh` (cron: `7 * * * *` — не в :00, чтобы не совпадать
с чужими пиками):

```bash
#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date -u +%Y%m%d-%H%M%S)
DIR=/opt/remnawave-backups
mkdir -p "$DIR"

# 1. Дамп базы. Имя контейнера БД проверить на месте: docker ps | grep db
docker exec remnawave-db pg_dumpall -U postgres | gzip -9 > "$DIR/db-$STAMP.sql.gz"

# 2. Конфиги и секреты стека
tar czf "$DIR/stack-$STAMP.tar.gz" -C /opt remnawave/.env remnawave/docker-compose.yml

# 3. S3 (rclone remote 'b2' настроить заранее: rclone config)
rclone copy "$DIR/db-$STAMP.sql.gz"    b2:fatvpn-panel-backups/hourly/
rclone copy "$DIR/stack-$STAMP.tar.gz" b2:fatvpn-panel-backups/hourly/

# 4. Telegram (свой бот-канал, НЕ рабочий бот)
curl -sf -F chat_id="$TG_CHAT" -F document=@"$DIR/db-$STAMP.sql.gz" \
  "https://api.telegram.org/bot$TG_TOKEN/sendDocument" > /dev/null

# 5. Ротация локальных копий и heartbeat: если скрипт молчит час — алерт
find "$DIR" -mtime +2 -delete
curl -sf "https://hc-ping.com/<uuid>" > /dev/null   # healthchecks.io, бесплатный
```

Шаг 5 обязателен: **бэкап, который молча перестал делаться, хуже отсутствующего** —
он создаёт ложную уверенность. healthchecks.io шлёт алерт в Telegram, если пинг не
пришёл вовремя.

Готовая альтернатива скрипту — [remnawave-backup-restore](https://github.com/distillium/remnawave-backup-restore)
(distillium): то же самое (директория + БД, расписание, Telegram, S3/GDrive,
retention) в готовом виде. Приемлемо; собственный скрипт прозрачнее на 30 строк.
Что бы ни выбрали — heartbeat-мониторинг поверх обязателен.

### 2.3 Тестовое восстановление — часть этапа, не «потом»

На чистой VM (можно временной, за €0.01/час): развернуть панель с нуля → залить
дамп → скопировать `.env` из бэкапа → войти в панель → увидеть пользователей и ноды.
Замерить время. Это репетиция ровно вчерашнего сценария.

**Готово, когда:**
- [ ] почасовой бэкап лежит в S3 **и** в Telegram, retention работает;
- [ ] healthchecks.io алертит при пропуске (проверено: закомментировать пинг на час);
- [ ] восстановление на чистой VM прошло, время записано (ориентир: < 30 мин);
- [ ] в бэкапе есть `.env`, и логин в восстановленную панель работает.

## 3. Этап 2 — серверы и сеть

### 3.1 Покупка

B и C — у **других** провайдеров, не у того, где A. Спецификация из §1.2. При выборе
проверить: провайдер не блокирует UDP 51820 (WireGuard) и даёт rescue/консоль
(пригодится для fencing, §7.1).

### 3.2 WireGuard-меш

Полный меш из трёх узлов, подсеть `10.77.0.0/24`: A=`10.77.0.1`, B=`.2`, C=`.3`.
`PersistentKeepalive = 25` (NAT здесь нет, но узлы за строгими firewall).
Репликация Postgres и всё межсерверное — **только** по этим адресам; Postgres на
публичных интерфейсах не слушает вообще.

Firewall каждого сервера панели: наружу открыты 80/443 (+SSH со своих IP), 51820/udp
для двух других узлов; порт Postgres — только на WG-интерфейсе.

**Готово, когда:**
- [ ] `ping 10.77.0.x` ходит между всеми парами, переживает перезагрузку узла;
- [ ] `pg_isready -h 10.77.0.1` с B и C — ок; с публичного IP порт Postgres закрыт
      (проверить nmap'ом снаружи).

## 4. Этап 3 — репликация Postgres

Потоковая физическая репликация, primary A → standby B и C, с репликационными
слотами (слот гарантирует, что primary не выкинет WAL, пока отставший standby его
не забрал — цена: следить за диском, см. мониторинг §9).

### 4.1 На A (primary)

В конфиг Postgres контейнера панели (`postgresql.conf` или command-флаги compose):

```
wal_level = replica          # дефолт в PG 14+, проверить
max_wal_senders = 5
max_replication_slots = 5
wal_keep_size = 1GB
```

`pg_hba.conf` — только WG-адреса:

```
host  replication  replicator  10.77.0.2/32  scram-sha-256
host  replication  replicator  10.77.0.3/32  scram-sha-256
```

Пользователь: `CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD '<...>';`
Слоты: `SELECT pg_create_physical_replication_slot('standby_b');` (и `standby_c`).

Порт наружу из контейнера — публиковать **только на WG-адрес**:
`"10.77.0.1:5432:5432"` в compose панели.

### 4.2 На B и C (standby)

```bash
docker compose stop remnawave-db   # и панель там вообще не запущена
docker run --rm -v remnawave-db-data:/var/lib/postgresql/data postgres:16 bash -c \
  'rm -rf /var/lib/postgresql/data/* && \
   pg_basebackup -h 10.77.0.1 -U replicator -D /var/lib/postgresql/data \
     -X stream -R --slot=standby_b -C'
docker compose start remnawave-db
```

`-R` пишет `standby.signal` + `primary_conninfo` сам. На C — то же со `standby_c`.
Имя тома смотреть в компоузе панели на месте.

⚠️ Мажорная версия Postgres на всех трёх — **одна и та же, до минора не критично,
до мажора обязательно**. Физическая репликация между разными мажорами не работает.
Зафиксировать версию тегом образа в compose, не `latest`.

### 4.3 Проверка

На A: `SELECT client_addr, state, replay_lag FROM pg_stat_replication;` — две строки
`streaming`, lag < 5 с. На B: создать тестового пользователя в панели на A и увидеть
его строку в standby-базе через `psql` за секунды.

**Готово, когда:**
- [ ] оба standby в `streaming`, replay_lag < 5 с под обычной нагрузкой;
- [ ] тестовая запись на A видна на B и C в течение 10 с;
- [ ] рестарт Postgres на B → сам вернулся в `streaming` без рук;
- [ ] обрыв WG-туннеля на 10 минут → standby догнал после восстановления (слот
      удержал WAL), диск на A это пережил.

## 5. Этап 4 — три идентичные панели

Резерв обязан быть **бинарно и конфигурационно идентичен** активному, иначе в момент
аварии вместо переключения будет отладка.

| Что | Требование | Что будет, если нет |
|---|---|---|
| Версия образа Remnawave | Одинаковый тег на всех трёх; обновление панели = обновление всех трёх в один день (сначала B/C — их простой ничего не стоит, потом A) | Промоушен на старую версию → миграции «из будущего» в базе, панель не стартует |
| `APP_SECRET` / JWT-секреты в `.env` | **Побайтно одинаковые** | 403 на логин; ноды не принимают панель; все выданные токены невалидны |
| TLS-сертификат `z.fatvdsnvv.space` | Выпущен **заранее на всех трёх** через **DNS-01** (acme.sh / certbot с Cloudflare API-токеном), авто-продление на каждом | HTTP-01 на пассивном узле не пройдёт никогда (домен смотрит на A) → резерв поднимается без валидного серта → приложение и бот получают TLS-ошибку вместо панели |
| compose/конфиги | В git (приватный repo) или синхронизированы скриптом; руками по трём серверам — не вариант | Дрейф конфигурации, всплывающий только при аварии |
| Панель на B и C | **Остановлена**, автостарт выключен (`restart: "no"` на пассивных или `systemctl disable` враппера) | Резерв, сам стартующий при перезагрузке, — готовый второй primary и split-brain |

### 5.1 sub.fatklyuchi.space

Origin Yandex CDN должен указывать на **домен** панели, не на IP сервера A — тогда
фейловер панели прозрачно чинит и страницу подписки. Проверить в настройках CDN;
если там IP — поменять на домен в этом же этапе.

### 5.2 BFF и бот при фейловере

Ничего менять не нужно — и это надо **сохранить**: BFF ходит в панель по
`https://z.fatvdsnvv.space` (домен, не IP), бот — через BFF. Правило на будущее:
**ни один клиент панели никогда не конфигурируется её IP-адресом.** Появится соблазн
«захардкодить, чтобы не зависеть от DNS» — он ломает весь фейловер.

**Готово, когда:**
- [ ] `diff .env` между A/B/C — расходится только hostname-специфика (в идеале ничего);
- [ ] на B и C лежит валидный серт `z.fatvdsnvv.space`, `openssl x509 -enddate` > 30 дней,
      авто-продление в кроне отработало хотя бы раз (форсировать `--force-renewal`);
- [ ] панель на B, запущенная руками в тестовом окне со своим локальным Postgres
      (промоушен копии), пускает в админку и показывает данные;
- [ ] автостарт панели на B и C выключен, перезагрузка сервера её не поднимает.

## 6. Этап 5 — ноды и Cloudflare Load Balancer

### 6.1 Firewall нод — заранее, на каждой

Панель управляет нодой по `NODE_PORT` (2222/tcp), и порт должен быть открыт только
для панели. Значит **на каждой ноде — все три** публичных IP:

```bash
ufw allow from <IP_A> to any port 2222 proto tcp
ufw allow from <IP_B> to any port 2222 proto tcp
ufw allow from <IP_C> to any port 2222 proto tcp
```

Без этого резервная панель поднимется, покажет админку — и не сможет управлять ни
одной нодой. Это обнаружилось бы ровно в момент аварии. Новая нода в будущем =
сразу три правила (внести в процедуру добавления ноды).

### 6.2 Cloudflare Load Balancer

Требование: зона `fatvdsnvv.space` должна обслуживаться в Cloudflare. **Сейчас это
не подтверждено** — открытый вопрос №1 (§12). Если домен не в CF — либо перенести
(nameserver'ы, как уже сделано с `fatklyuchi.space`), либо §6.3.

Настройка (Traffic → Load Balancing):

- **Monitor**: HTTPS GET `/` (или путь логин-страницы панели), интервал 15 с,
  timeout 5 с, retries 2, ожидаемый код 200–399, проверка из 2–3 регионов.
- **Pools** (по одному origin в каждом): `panel-a`, `panel-b`, `panel-c`.
- **Load Balancer** на hostname `z.fatvdsnvv.space`: режим **failover** — порядок
  пулов A → B → C; **Proxy OFF (DNS-only, серое облако)**, TTL 30 с.
- Notifications → алерт в Telegram/почту при смене здоровья пула.

DNS-only здесь — осознанный выбор: LB меняет DNS-ответ на здоровый origin, оранжевое
облако не участвует. Правило проекта «серые облака, и только серые» (оранжевое убило
ноды единственный раз, когда его включили) остаётся в силе без исключений — так его
не надо помнить с оговорками. Цена: $5–15/мес (2 origin включены в базовые $5,
третий — доплата).

⚠️ Что LB **делает и чего не делает**: он переводит **трафик** на B за ~30–60 с
(health-check + TTL). Он **не** промоутит базу и **не** запускает панель — это §7.
До промоушена B отвечает connection refused, что для клиентов неотличимо от простоя.
Поэтому время фейловера системы = время реакции человека на алерт + 5 минут ранбука,
а не «30 секунд» (пока не сделан этап-2 автопромоушен, §7.3).

### 6.3 Если Cloudflare для этой зоны недоступен

Запасной вариант — свой наблюдатель (по образцу того, что уже работает у бота):
скрипт на **независимом** от всех трёх серверов узле (например, сервер BFF), проверка
`https://z.fatvdsnvv.space/` каждые 30 с, при N подряд отказов — перепись A-записи
через API DNS-провайдера (TTL заранее 60 с) + алерт. Хуже CF LB ровно тем, что
наблюдатель — наш код и наша новая точка отказа; выбирать только при недоступности LB.

**Готово, когда:**
- [ ] на каждой ноде `nc -zv <нода> 2222` проходит с A, B и C (проверить с самих серверов);
- [ ] LB создан, monitor «зелёный» на A, «красный» на B/C (панель там и должна лежать) —
      и режим failover при этом держит DNS на A (проверить `dig z.fatvdsnvv.space`);
- [ ] алерт о смене здоровья пула приходит в Telegram (проверено остановкой панели на A
      в тестовое окно);
- [ ] `dig` с TTL ≤ 60.

## 7. Этап 6 — переключение (промоушен) и возврат

### 7.1 Ранбук фейловера — одна страница, отрепетированная

Печатается и кладётся туда, где его найдут в 3 часа ночи. Порядок жёсткий:

```
0. Убедиться, что A действительно мёртв, а не «медленный»:
   - панель не отвечает С ДВУХ разных сетей;
   - SSH на A не ходит / провайдер показывает down.
   Если A жив, но деградировал — сначала лечить A, промоушен не делать.

1. FENCING — отсечь A, чтобы он не вернулся primary'м самовольно:
   - если есть доступ: на A `docker compose down` (панель + БД) и запретить автостарт;
   - если доступа нет: выключить сервер через панель провайдера (power off);
   - НЕЛЬЗЯ продолжать, пока не сделано одно из двух. Вернувшийся A с живой
     панелью = split-brain, авария хуже простоя.

2. На B промоутить Postgres:
   docker exec remnawave-db psql -U postgres -c "SELECT pg_promote();"
   → проверить: SELECT pg_is_in_recovery();  -- must be false

3. На B запустить панель:
   docker compose up -d
   → открыть https://z.fatvdsnvv.space (DNS уже переведён LB'ом), войти,
     убедиться, что ноды в панели зелёные (это заодно проверка §6.1).

4. Перевести репликацию C на нового primary B:
   на C: ALTER SYSTEM SET primary_conninfo = 'host=10.77.0.2 ...';
         создать слот на B, рестарт Postgres C, проверить pg_stat_replication на B.
   Некритично для восстановления сервиса — можно через час, но не «завтра»:
   до этого C отстаёт и не является резервом.

5. Сообщить в чат: что, когда, кто промоутил. Бэкап-cron включить на B (§7.4).
```

Пункты 2–3 оформить скриптом `promote.sh` на B и C — но **запускаемым руками**.
Автоматика здесь — этап 2 (§7.3).

### 7.2 Возврат (failback) — без спешки

Пока жив B, система полноценна (C — его standby). A возвращается **как standby**:
чистый `pg_basebackup` с B (старые данные A выбрасываются — после промоушена B их
таймлайны разошлись), затем в спокойное окно — обратный промоушен по тому же
ранбуку, если вообще нужен: система симметрична, «главного» сервера нет.

### 7.3 Этап 2 (после успешных учений): автопромоушен

Если заказчику нужно строго «само, без человека» — Patroni (или repmgr) поверх тех
же трёх Postgres: три узла дают кворум, split-brain решается протоколом, промоушен
за секунды; поверх — хук, поднимающий панель на новом primary. Это существенный
объём (свой etcd/consul или встроенный DCS, обвязка в контейнерах панели), и ставить
его надо **на работающую и отрепетированную** ручную схему, а не вместо неё.
Решение — после учений §8, с замером: если ручной фейловер укладывается в 10–15
минут с алертом в Telegram, возможно, этого достаточно.

### 7.4 Бэкапы при фейловере

Cron бэкапа (§2) стоит на всех трёх, но активен только на текущем primary (шаг
скрипта: `pg_is_in_recovery()` → standby молча выходит, **и не пингует heartbeat** —
пинг с standby маскировал бы умерший бэкап на primary). Проверка «бэкап едет с B»
входит в учения.

## 8. Этап 7 — учения. Без них всей схемы нет

Каждое учение — с секундомером и записью результата в этот документ. Проводить в
окно минимальной нагрузки, с предупреждением заказчика.

| # | Сценарий | Что делаем | Успех |
|---|---|---|---|
| У1 | Восстановление из бэкапа (репетиция вчерашнего) | Чистая VM + дамп из S3 + `.env` из бэкапа | Логин работает, данные на месте, время < 30 мин |
| У2 | Мягкий отказ | На A: `docker compose stop` панели | Алерт CF < 2 мин; DNS уехал на B; ранбук §7.1 выполнен; система жива; общее время записано |
| У3 | Жёсткий отказ (вчерашний сценарий) | Power off сервера A через панель провайдера, без подготовки | То же. Отдельно проверить: ноды остались зелёными в панели на B; приложение подключается; бот выдаёт ключ; sub-страница открывается |
| У4 | Возврат | A обратно как standby, затем обратный промоушен в окно | Оба перехода без потери данных (тест-пользователь, созданный «при B», виден после возврата на A) |

## 10. Бот: третий резервный сервер

У бота уже есть основной + запасной с автопроверкой и переключением. **Схема этого
механизма в репозитории не описана** (бот живёт только на сервере, `/opt/FatVPN`),
поэтому здесь — принцип и вопросы, а не конфиги:

1. **Изучить существующий механизм** прежде, чем строить третий узел: что проверяет
   (getUpdates? свой health?), кто проверяет (внешний наблюдатель? сами узлы друг
   друга?), как передаётся роль (у Telegram-ботов это обычно «кто держит polling» —
   два одновременно живых polling'а на один токен вызывают конфликт 409, что удобно:
   сам Telegram выступает арбитром).
2. **Третий узел — копией второго**, включённой в ту же цепочку проверки: A умер →
   B, B умер → C. Если текущая схема — «B проверяет A», её надо превратить в кольцо
   или вынести наблюдателя, иначе C не узнает о смерти B.
3. **Состояние бота.** Критичный вопрос: что бот хранит локально (SQLite? файлы?
   свой Postgres?) и как это попадает на резервы. Если резервный бот поднимается с
   пустой/старой базой — переключение «работает», но данные (незавершённые оплаты,
   состояния диалогов) теряются. Ответ определяет, нужна ли боту репликация или
   достаточно того, что его истинное состояние живёт в панели и BFF.
4. Бэкапы бота — в ту же систему §2 (S3 + Telegram + heartbeat), со всех узлов.

**Готово, когда:** третий узел в цепочке; учение «выключили A и B — бот отвечает
с C» пройдено; состояние при переключении не теряется (или письменно
зафиксировано, чем жертвуем).

## 11. За рамками задачи, но обязано быть сказано: BFF

`87.121.221.229` — BFF + его Postgres (аккаунты, сессии, refresh-токены, триалы,
слоты устройств) + Caddy + бот. Один сервер. **Бэкапов нет.** Его отказ = приложение
не работает ни у кого; потеря его диска = все залогинены заново в лучшем случае,
потеря учёта триалов и слотов — в худшем.

Минимум, который надо сделать **в этом же заходе, в день этапа 1** (§2), потому что
это +30 минут к уже написанному скрипту: тот же почасовой `pg_dump` fatvpn-postgres

Полноценный резерв BFF (второй сервер, реплика, тот же CF LB на
`api.fatklyuchi.space` — зона **уже в Cloudflare**, что упрощает) — отдельная задача
после панели. Одно предостережение на тот день: приложение пинит **CA** (ISRG), не

но серт на резерве должен быть выпущен так же заранее и так же через DNS-01 (§5).

## 14. Чего этот план сознательно не обещает

Чтобы ожидания заказчика совпали с реальностью:

- **«Ноль простоя» не бывает.** Реалистичная цель этой схемы: обнаружение < 2 мин,
  сервис восстановлен < 15 мин (ручной промоушен) или < 2 мин (после этапа
  Patroni). Уже подключённые VPN-клиенты простоя панели вообще не замечают.
- **Потеря последних секунд записей возможна.** Асинхронная репликация: транзакции,
  закоммиченные на A в последние секунды перед смертью, могли не доехать до B.
  Синхронная репликация это лечит ценой того, что смерть standby останавливает
  запись на живом primary — для этой системы размен невыгоден.
- **Переключение не мгновенное для всех.** DNS-кэши уважают не все резолверы; TTL
  30 с означает «большинство клиентов за минуту», не «все за 30 секунд».
- **Схема требует дисциплины эксплуатации:** обновление панели — на всех трёх в
  один день; новая нода — сразу три firewall-правила; квартальное учение У2.
  Нарушение любого из трёх тихо превращает резерв в декорацию — это главный
  долгосрочный риск всей конструкции.
