# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

FatVPN is a cross-platform VPN app (Flutter mobile + .NET 10 BFF + Telegram bot) fronting a **Remnawave** VPN panel. The Android app is feature-complete and device-tested: pairing onboarding, on-the-fly trial (2 days, `Trial:DurationDays`), real sing-box VPN tunnel, split tunneling, live server ranking, local expiry reminders (client-scheduled `flutter_local_notifications`, no FCM), EN/RU. Auth uses an access+refresh token split with a "subscription expired → renew" screen (e2e-verified on emulator 2026-07-08). **iOS is now feature-complete and device-tested too** (2026-07-24): sing-box tunnel via a `PacketTunnel` Network Extension, split tunneling by domain/IP (per-app is impossible on iOS without MDM), DNS-leak/background/network-switch validated on a real iPhone; built via Codemagic → TestFlight (build 18). ⚠️ That validation covered "the tunnel carries traffic", not "the tunnel is correct": it never tested IPv6 leaks, a network switch **under load**, whether disconnecting actually restores the internet, recovery from a killed extension, or what stays on disk after logout — which is how the 2026-07-27 audit found three criticals in code that had passed. The audit remediation (2026-07-28) touches every layer of the iOS tunnel — including the TUN stack (`gvisor` → `system`), MTU, on-demand/kill-switch and the extension lifecycle — and **it compiles but has never been run**: Codemagic `ios-release` went green as **build 136** (2026-07-28), which proves the Swift builds, the `analyze && test` gate passes on CI, and the App Groups entitlement survives re-signing into the exported `.ipa` — and proves nothing about behaviour, since a broken tunnel compiles exactly as well as a working one. Treat build 18 as the last iOS data point about *behaviour*, and build 136 as the first about *buildability*. See `docs/ios-vpn-tunnel-spec.md` for the iOS story (its Phase 7 section now records what the validation did not cover) and `docs/app-bff-integration.md` for the full status log. That remediation was then **read back line by line (2026-07-28)** and 30 defects were found *in the fixes themselves* — 16 corrected on the spot and the other 14 (V17–V30) the next day, 2026-07-29, all listed under "Вычитка ремедиации" in `docs/improvement-plan-ios.md`. None of the 14 has been run on a device: they are Dart under host tests and Swift that has only ever met a compiler. Two of those were CI defects that build 136 then exercised: the quality gate had no `set -e`, so a failing `flutter analyze` was printed and published anyway, and the App Group entitlement check read the archived bundle instead of the re-signed `.ipa` and passed green when it found nothing. The heaviest of them was V17: logout-by-401 and subscription-expiry (402) bypassed the persisted-state wipe, which on iOS with on-demand meant the OS could raise the tunnel on credentials the panel had already revoked — closed 2026-07-29 by `VpnController.stopAndForgetStandalone()` plus a fallback in `AuthController` covering every way a session dies, and waiting on T15 for its first real test. **Home-screen widget: Android and iOS** (`docs/home-widgets-spec.md`). The Android app widget renders a snapshot — state, location, session clock — written by the app and, when the app is not running, by the tunnel itself (the plugin's state broadcast). The power button is a **separate** control — a tap anywhere else on the widget only opens the app — and it works in both directions: it disconnects natively and **connects natively too**, by running the app's own connect code in a background Flutter engine (`WidgetConnectService` → `widgetConnectMain` in `lib/main.dart` → `WidgetConnectRunner`), so raising the tunnel still does the live 402 entitlement check and fetches a fresh config instead of reusing the one on disk. It opens the app only where a screen is unavoidable: no session, a lapsed subscription, or the first-ever VPN consent dialog. With no country chosen — every first press — it connects to the fastest node overall; the choice persists (`SelectedLocationStore`, cleared on sign-out). Android offers **two sizes in the picker** — the 4×2 card and a 2×2 square (`FatVpnWidgetSquareProvider`, an empty subclass: a provider's default size lives in its `appwidget-provider` XML and there is one per receiver) — drawn by three layouts the launcher picks between by the tile's actual size. The press has an answer of its own, because a connect takes seconds and until it lands the tile would redraw exactly what it drew before — indistinguishable from a dead button: the direction of the tap is written down (`stopRequestedAt`/`connectRequestedAt`) and drawn over the real state until the tunnel speaks for itself, the disc got a ripple, and the tap buzzes via `WidgetHaptics` using `USAGE_HARDWARE_FEEDBACK` — the tap lands in a broadcast receiver, i.e. always a background process, where the platform silently drops any vibration whose usage is not on a short allow-list, so the semantically neater `USAGE_TOUCH` would ship a button that never buzzes. **The Android widget was run on a device for the first time on 2026-08-03 and its button works** — connect from the widget, disconnect, and a press with the app swiped away, plus the tile redrawing itself; before that day it had never been seen past the "disconnected" state. That run also exposed what the app says about **a tunnel it did not personally start or stop**, which no test covered because until the widget there was no such tunnel: `_sessionStartedAt` was cleared only by an in-app power-off, so every other ending (widget button, notification Stop, a killed process, a reboot) left the start on disk and the next connect inherited it — thirty seconds of tunnel reading `09:34:33` — and a relaunch onto a live tunnel left `connectedNode` null, so the card said "Подключено к Лучший сервер" while plainly on a specific node. Fixed in `3c5e487` and **verified on a device**: a new session is anchored where the tunnel comes up unless a teardown seconds earlier declared this connect continues one (a deadline, not a flag — a flag nobody clears would preserve the clock across the next real session too), and the node is persisted and restored, with the restore notifying listeners itself because the reconciliation around it only fires on a *state* change and by then there usually isn't one. **The iOS WidgetKit extension was removed on 2026-08-01 and written again from scratch the same day**, with the press being a link on iOS ≤17 and, since 2026-08-04, the **sing-box architecture** on iOS 18+ — a plain widget-process App Intent driving `NETunnelProviderManager` natively (see below). **`fatvpn://widget/toggle`** — it opens the app and reaches Dart through the engine's own deep-link channel (`FlutterDeepLinkingEnabled` + `didPushRouteInformation` → `AuthController._handleUri`, with the launch URL held natively in the scene delegate for a cold start), the one path this app has carried end-to-end on a device, and **confirmed working on an iPhone 11 / iOS 17.6.1 (build 207)**. **The app-process App Intent (`AudioPlaybackIntent`) was deleted on the morning of 2026-08-03, restored the same evening on the owner's reversal, and buried for good on 2026-08-04**, when the owner's own iOS 18+ phone answered the restored hybrid with the same failure as every build before it — the press threw the user into the app and toggled nothing. That was the acceptance verdict the restore itself had set («a traced run, or the link for good»), so **that routing gets no third comeback** — the 18+ button that exists now is a different architecture, not that one back (see below). Buried with the old scheme: `FatVpnWidgetHaptics.swift`, `Runner/FatVpnWidgetToggle.swift`, the `fatvpn/widget_connect_host` channel, the raw `-weak_framework AppIntents` ldflag and `UIBackgroundModes: audio`. It never ran on iOS 17: the native press trail, written to the App Group on `perform()`'s first line before anything can fail, came back empty under every marker Apple documents (`ForegroundContinuableIntent`, `LiveActivityIntent`, `AudioPlaybackIntent`) and then under `openAppWhenRun: true` with no `widgetURL` on the tile (build 206). On iOS 18 it failed on three separate occasions with one signature — opens the app, toggles nothing, no haptic, i.e. a `perform()` that never ran: build 207 (no background modes), build 233 from a user's phone (`audio` mode aboard since 208), and the owner's own iOS 18+ phone on 2026-08-04 on the restored hybrid; the one «works on 18» report (2026-08-03) was retracted by the tester the same day. **What replaced it on 18+ (2026-08-04, owner's call after a four-way web research pass): the sing-box architecture.** The research established three things. (1) The app-process route (`AudioPlaybackIntent`/`openAppWhenRun`/`LiveActivityIntent`) is broken ecosystem-wide — iOS 17 with the app alive (Apple forums 732771/735159), iOS 18 outright (758784) — and sing-box had to *remove* that conformance from their own toggle to make it work (commit dac24338). (2) The only field-proven background VPN toggle is a plain intent performed **in the widget extension's own process**, calling `NETunnelProviderManager` load/save/start/stop directly — sing-box VT, Tailscale and Shadowrocket all ship it that way (as iOS 18 Control Center controls), and the widget needs **no NetworkExtension entitlement** for it (sing-box's widget carries only the App Group) — so this project's old axiom «a widget can never touch the tunnel» is disproven by shipping code. (3) Our old intents likely also shipped **broken metadata**: Xcode 15.3+ deployment-aware processing is Apple-acknowledged broken for targets with min deployment ≤ iOS 15 (Runner deploys to 13) — it emits an empty `mangledTypeName`, the system cannot resolve the type, and the press falls through to «open the app» (thread 751229, FB13664020); additionally a raw `-weak_framework AppIntents` in OTHER_LDFLAGS is invisible to appintentsmetadataprocessor. The new scheme: `FatVpnTunnelToggleIntent` (home-screen button, 18+ only — ≤17 keeps the link) and `FatVpnTunnelSetIntent` (a Control Center `ControlWidgetToggle`, `FatVpnWidgetControl.swift`), both plain, both performing in the widget process via `FatVpnWidgetTunnel.swift` — native stop clears on-demand first and parks a `wasOnDemandEnabled` marker the native start restores; native start passes no options, riding the same persisted `start_options.plist` snapshot an on-demand start uses (wiped on logout/402, refused after 7 days), so **a widget connect performs no live 402 check** — the accepted price; with no VPN consent yet the press does nothing but trace (first connect must be in-app). Both build defects are fixed in `add_widget_target.rb` (`ENABLE_APPINTENTS_DEPLOYMENT_AWARE_PROCESSING=NO` on Runner and widget; AppIntents linked as a Weak frameworks-phase entry), and the CI step `Verify the widget intents shipped with usable App Intents metadata` parses `extract.actionsdata` in **both** bundles and fails on a missing intent or an empty `mangledTypeName` — the old name-grep gate passed while the button shipped dead. ⚠️ **The new 18+ scheme has never been on a device** (Swift compiles only on CI); acceptance is TW10 (reinstall the tile first — WidgetKit archives the view) + TW14 with a trace (`press → native toggle (widget process)` / `native start issued`) + TW14a (the Control Center toggle — the surface where this demonstrably works for others; if it works and the tile button does not, the fault is WidgetKit press delivery, not our metadata). Known residual risk: even extension-process presses went dead on iOS 18.0.x for sing-box (issue #2245 - four fix iterations and STILL OPEN as of 2026-08-04; iOS 26.x adds confirmed point-release press-delivery regressions, FB22848510). Precision note from the 2026-08-04 re-research: sing-box ships ONLY a Control Center control - their WidgetExtension has no home-screen button - so the field-proven surface is the control (TW14a first), and the tile button is our own extrapolation; since that night the whole tile is the button, the glyph is pinned full-colour against the iOS 26 accented-Image-in-Button bug, and the trace names its process by bundle id. LATE 2026-08-04: the first traced run of the new scheme (build 245, iPhone 15 / iOS 26.5.2) came back with an EMPTY widget-process trail - perform() never ran, matching Apple's confirmed 26.5 press-delivery regression FB22848510 - and the owner moved the version split from 18 to 26: iOS <=18 presses the tile as the fatvpn://widget/toggle link (the only mechanism with positive device data; the native scheme has no positive 18.x run either), iOS 26+ keeps the native background button with the FB22848510 risk on record. The Control Center toggle stays native on 18+. Build 246 on that same iPhone 15 then flipped the story: the intent RUNS in the widget process (trace: press -> native toggle in ...FatVpnWidget), the native widget STOP works - the first on-device success of this architecture - and the native START died on START FAILED: Missing start options because we wiped the snapshot ourselves, twice over: stopTunnel(.userInitiated) erased it on every ordinary off-switch, and Dart disconnect(endSession: true) erased it again. Both wipes now belong only to session death (sign-out/401/402); a power-off keeps the snapshot and the clash secret with it (the widget start rides the snapshot's config, and the app needs its secret to probe). Contract re-pinned in ios_audit_tunnel_lifecycle_test.dart. **A build >= 247 then ran on that iPhone 15 (video, evening 2026-08-04) and the native toggle works in BOTH directions with the app never opening — the first complete on-device success of this architecture.** It left three defects, all three fixed the same night and none of them on a device yet. (1) **The tile stopped redrawing itself:** the tunnel was up at second 5 of the recording and the tile still said "Подключение…" at second 10, when the app was opened; same on the way down. The record on disk was right — the packet-tunnel extension patches it on every start and stop — but the `reloadAllTimelines()` beside that patch never reaches WidgetKit from an NE process, so nothing re-rendered. The timeline now **asks the OS itself** (`FatVpnWidgetTunnel.liveState()` → `NETunnelProviderManager`, merged over the stored record, which still owns location/language/session) and asks for a 10-second refresh while the state is in motion instead of 15 minutes; and the press waits for its own outcome (`publishWhenSettled`, ≤6 s start / ≤4 s stop) and patches from the widget process, where a reload demonstrably lands. The lesson generalises: **a snapshot the widget reads for itself needs no delivery** — cross-process reload requests are a message, and messages get lost. (2) **A press on the disc opened the app while a press on the text toggled** — on a tile that is one whole-tile `Button(intent:)`, so the only thing under the disc and nowhere else is the `Image(systemName:)` carrying `widgetAccentedRenderingMode`, the modifier at the centre of Apple's unfixed reports of buttons that stop firing. The disc is now `allowsHitTesting(false)` inside the tile button (it is pixels; the press belongs to the ancestor) and `contentShape(Circle())` where it is the button (medium tile). Falsifiable: if presses still miss, the fault is WidgetKit press delivery (FB22848510) and the next move is a `widgetURL` fallback. (3) **The session clock lied** — `00:00:46` on a seven-second-old tunnel, because `VpnController.connect` anchors the session and a native start never reaches Dart, so the app inherited the previous session's start. The press now leaves its start in the App Group (`markNativeSessionStart`), the app takes it once on the next reconciliation (`takeNativeSessionStart` → `_adoptNativeSessionStart`) and only ever moves the anchor forward, so a reconnect that deliberately continues a session (`endSession: false`) cannot be overruled; pinned by `test/ios_widget_native_session_test.dart`. **All three were then confirmed on the device the same evening** (iPhone 15 / iOS 26.5.2, the build carrying `e17395a`): the tile reaches "Подключено" with a running clock **on its own** and "Отключено" on its own, the app never opening; a press **on the disc** toggles instead of opening the app; and the session clock matches the tunnel's real age. That is the first complete acceptance run this iOS widget has ever had — every earlier "it works" covered one half. What is still open is the owner's next request, **a haptic on the press**: Apple offers no haptic API for a widget's interactive controls (forum thread 731292, "haptic feedback does not work in interactive widgets"; one App Store app is observed doing it anyway with no account of how), so `FatVpnWidgetHapticTap` tries two public paths in order — Core Haptics (one transient tap) then `AudioServicesPlaySystemSound(1519)`, the "peek" actuation — and records in the trail which one ran, called on `perform()`'s second line because a press answered three seconds late is not answered. ⚠️ It may not fire at all; if the trail says `core haptics` and nothing was felt, the order is what changes. The same night the owner also settled the tap target by circling the disc in both sizes: **the button is the disc, not the whole tile** (that arrangement lasted one build), a tap anywhere else opens the app — which is WidgetKit's default with `widgetURL` left nil, and nil it stays, because a `widgetURL` is reported to swallow presses landing on a `Button(intent:)` inside it (thread 731758, and `db87370` is this project losing a button to exactly that) — and the disc grew 62 → 76pt on both families. On ≤18 the whole tile still toggles: there the press is a link and `systemSmall` gets exactly one tap target, so the asymmetry is the platform's. The `Image(systemName:)` inside the disc is now `allowsHitTesting(false)` unconditionally: it is drawn, never pressed, and it was the prime suspect for a press on the disc that reached WidgetKit's "no control here" default instead of the control it landed on. Two things came free: the `audio` background mode no longer has to be justified at App Store review (`docs/store-compliance.md`), and CI fails a build where it or `FatVpnTogglePowerIntent` reappears in the `.ipa`. The link half rests on real data: **builds 207 and 234 confirmed it on an iPhone 11 / iOS 17.6.1** (press opens the app and toggles the tunnel). The price:  the app comes to the front on every press, and a tap anywhere on the tile toggles rather than only the disc — `systemSmall` gets exactly one tap target from WidgetKit. Vibration comes from Dart `HapticFeedback` when the link arrives, iOS only — Android delivers the same link but has already buzzed in its broadcast receiver, and a second buzz would be felt as one press registering twice. The tile carries `.widgetURL` on ≤17 and drops it (nil) on 18+, where the button owns the press — a `.widgetURL` is reported to swallow presses landing on a `Button(intent:)` inside it (thread 731758). The moving parts: `ios/FatVpnWidget/` (view, strings, the two plain intents, the native tunnel helper and the Control Center control), `ios/Shared/FatVpnWidgetStore.swift` (App Group snapshot + press overlay + parked action + native press trail, compiled into all three targets), the `fatvpn/widget` channel in `AppDelegate.swift`, `ios/tool/add_widget_target.rb`, and the widget steps in `codemagic.yaml` — so iOS signing covers three bundle ids; CI keeps verifying that no `UIBackgroundModes` and no `FatVpnTogglePowerIntent` ship in the `.ipa`, since both belong to the dead app-process scheme and would come back quietly. Widget deployment target is 16.0 (below that there are no accessory widget families); Runner stays on 13.0 with `-weak_framework AppIntents`, without which the app would not launch at all on iOS 13–15. Codemagic `ios-release` went green as **build #96 → TestFlight 205**, which proves the Swift compiles, `add_widget_target.rb` rewrites `Runner.xcodeproj` cleanly, the App Group survives re-signing, and the bundles unpack as expected from the `.ipa` (that build still carried the intents; they were removed on 2026-08-03). **Build 205 then crashed on launch on an iPhone 11 / iOS 17.6.1**, and the trace named the line: `FatVpnWidgetStore.write` ← the `fatvpn/widget` channel closure. `HomeWidgetSnapshot.toMap()` sends Dart `null` for the four fields a fresh session lacks, Flutter's codec renders them `NSNull`, and `UserDefaults` takes property lists only — `NSInvalidArgumentException`, an ObjC exception Swift cannot catch, on the app's *first* publish before any screen. **The same unfiltered line was in the previous implementation**; it was dormant only because removing the widget removed the channel, so nothing on iOS ever called it. Fixed by `FatVpnWidgetStore.plistSafe` (drop `NSNull` keys — a missing key and a null one are the same to every reader, and `write` replaces the whole record), with the input contract pinned by a test. The standing lesson: **the native end of a platform channel must not trust the payload** — anything crossing from Dart into `UserDefaults` gets filtered. Build 206 then ran on the device and settled two things: the display half **works** (the tile shows state, country and the session clock, and redraws itself when the app connects — so the channel, the App Group and the snapshot are all sound), and the intent half does not, which is what moved iOS 17 onto the link. **Build 207 confirmed the link works on a device (iPhone 11 / iOS 17.6.1, 2026-08-01): the press opens the app and toggles the tunnel** — the first time this button has ever been confirmed working. ⚠️ Not separately exercised: each direction on its own, the haptic, a press with the app force-quit, and the whole **iOS 18** branch, which 17.6.1 never reaches. `docs/home-widgets-spec.md` §10 has the acceptance run, and its first step is "remove the widget from the home screen and add it back", because WidgetKit archives the view and no earlier attempt started there. Since build 208 the branch moved another eight commits (2026-08-02), and **a build carrying them was finally run on a device on 2026-08-03** — that is the run that settled the button on all three paths. The change that matters: `codemagic.yaml` grew an `ios-simulator` workflow that **smoke-tests the widget in a booted simulator on every run** (`simctl` installs the app, lists the extension, opens the URL), the widget's first automated coverage ever — and on its first working run it caught a real bug (`c44d0d7`): **a press that cold-starts the app did nothing.** Flutter delivers a link pushed into a *live* app via `didPushRouteInformation`, which is all `main.dart` listened on; the URL that *starts* the process arrives once through `defaultRouteName`, which nothing read. Build 207's device run never saw it because the app stayed alive in the background the whole time — i.e. the "confirmed working" data point covered only the working half, and the ordinary state of a VPN app whose widget someone presses is *not running*. The launch URL is now held natively in the scene delegate (`2fb5b6d`, `2654bf5`) and handed to Dart when it is ready. One thing the instrumentation settled and the simulator cannot test: iOS never delivers `simctl openurl` to the scene delegate there at all, so the CI URL check now fails only when the app is at fault (`47b0989`). Two collateral fixes from that investigation **stay**, because they were never widget-specific: `FlutterDeepLinkingEnabled` (every `fatvpn://` open used to crash Flutter's own deep-link navigator with a caught null-check, because it competed with `app_links`, which was then proven to deliver nothing at all on this scene-based iOS template — the engine's own channel is the one path a device has carried end-to-end into Dart), and the support bundle carrying tails of the previous log files. **The first bug reported from a real user's iPhone (build 186, 2026-07-31) was the app throwing away a session it had just been given**: the renew screen refreshes the expired trial session while `/pair/status` is polled, and `_doRefresh` applied that response unconditionally, so a rotation of the dead session landed on top of the paid one pairing had just delivered — twice in a row, which the user read as "the bot says connected but the app shows nothing". Fixed in `fa9bc8f`, and the mirror (a late `/pair/status` clobbering a pasted key) in `4d3530b`; shipped as TestFlight **188/189** and **confirmed working by the user on 2026-08-01** — the first behavioural data point on iOS since build 18, every release in between having proved only that it compiles. What that confirms is the reported flow (pick a key in the bot after the trial lapses, come back to the app); the mirror path — start pairing, abandon it, paste the key instead — was not separately exercised. Two lessons worth keeping: the user's account of which button they pressed was wrong and the prod tables (`PairingCodes.Status`, abandoned `RefreshTokens` chains) were what actually diagnosed it; and any `await` whose result is written to shared state needs a recency check, because every session-replacing path (pairing, pasted key, trial, sign-out) races every other. Remaining (non-iOS): trial reinstall anti-abuse (the Android stopgap hashes `ANDROID_ID`; real Play Integrity / App Attest waits on store accounts) and the prod migration — **certificate pinning is written** (2026-08-02, CA-anchor pinning; see the Key Design Decisions entry) but has not been through TA17 on a device — HTTPS and the domain are done (2026-07-30, see the Production Server section). Work merged into `master` (pairing onboarding fast-forward 2026-07-09; iOS via squash 2026-07-24).

## Commands

All commands run from the `backend/` directory unless noted.

```bash
# Start Postgres (required before running the API). Name the service: a bare
# `up -d` would also start the bff and caddy containers, which is what the
# server wants and a developer running `dotnet run` does not.
docker compose up -d postgres

# Build
dotnet build FatVpn.Bff.slnx

# Apply EF migrations
dotnet ef database update --project src/FatVpn.Bff.Infrastructure --startup-project src/FatVpn.Bff.Api

# Add a new migration
dotnet ef migrations add <MigrationName> --project src/FatVpn.Bff.Infrastructure --startup-project src/FatVpn.Bff.Api

# Run the API (http://localhost:5030)
dotnet run --project src/FatVpn.Bff.Api

# Set Remnawave API token (required once per machine, not in git)
cd src/FatVpn.Bff.Api
dotnet user-secrets set "Remnawave:ApiToken" "<token>"
```

Manual API testing: `src/FatVpn.Bff.Api/FatVpn.Bff.Api.http` has VS Code REST Client requests for every endpoint.

Tests: `dotnet test tests/FatVpn.Bff.Tests/FatVpn.Bff.Tests.csproj` — **156 tests**, all green with Docker up (the Testcontainers ones **skip** without it, so a "0 skipped" run is the only proof the concurrency tests actually ran; last verified 2026-08-02). Four of them (`DeploymentConfigTests`) assert on `docker-compose.yml` rather than on code: `AllowedHosts` is no longer `*`, and a name dropped from that list answers **400** to everything arriving under it — `fatvpn-bff` is how the bot reaches the BFF, the bare IP is how already-installed builds do. The app side is **293 Dart tests** (1 skipped) via `flutter test` in `app/`, plus **213** in `app/packages/singbox_mm/` (measured 2026-08-03). One of them, `audit_best_node_test.dart`'s "candidates are measured concurrently", is timing-sensitive on a slow machine — it measures wall-clock overlap, so treat a single red run as noise and re-run before chasing it.

`Microsoft.OpenApi` is pinned to **2.7.5** by a direct reference in `FatVpn.Bff.Api.csproj`, purely to override the 2.0.0 that `Microsoft.AspNetCore.OpenApi 10.0.9` drags in — that one carries NU1903 / GHSA-v5pm-xwqc-g5wc (high). 2.7.5 is the first patched release on the 2.x line, per the advisory itself: 2.0.1 is still affected, which a restore confirms. Drop the pin once the framework package ships a patched dependency of its own.

- Unit/controller tests run on **SQLite in memory**, not the EF InMemory provider: InMemory ignores
  unique indexes and cannot execute `ExecuteUpdate`, so it could not exercise the atomic
  claim-and-rotate paths at all.
- `ConcurrencyIntegrationTests` spin up a real PostgreSQL via **Testcontainers** and hammer
  `/pair/status`, `/auth/refresh`, `/trial`, `/auth/token` and the account upsert with parallel
  callers. They need Docker running and **skip** (not fail) without it.

### Flutter app (`app/`)

```bash
# Get dependencies
cd app
flutter pub get

# List devices / emulators
flutter devices
flutter emulators

# Launch the Pixel 7 API 35 emulator
flutter emulators --launch pixel_7_-_api_35_0

# Run on a specific device
flutter run -d emulator-5554
```

- Android SDK lives at `C:\Android\Sdk` (moved off the default `%LOCALAPPDATA%` path because it contained a space, which breaks NDK tooling). `flutter config --android-sdk` points at it.
- Org/package id: `com.fatvpn.fatvpn_app`.
- **Release signing** (`cfe1f2b`): the keystore and its passwords live in `app/android/key.properties`, which is gitignored along with `*.jks`. A checkout **without** that file still builds — it falls back to the debug key and logs that it did — so `flutter run --release` works on a fresh clone and on CI. Before publishing, confirm the signature is real (`./gradlew :app:signingReport`, or `apksigner verify --print-certs` must not show `CN=Android Debug`).
- **Release ABIs:** x86/x86_64 are excluded from `release` via the Variant API (`androidComponents.onVariants(selector().withBuildType("release")) { variant.packaging.jniLibs.excludes }`), and the bundle splits by ABI and density (language split is off — Flutter ships its own localizations). ⚠️ Do **not** "simplify" this to `ndk { abiFilters }`: AGP takes the **union** of `abiFilters` across `defaultConfig` and the build type, and the Flutter Gradle plugin populates `defaultConfig` — so a filter there widens the set instead of narrowing it (verified: the AAB still shipped x86_64). Debug stays universal so it installs on the x86_64 emulator. Ship `flutter build appbundle`, not a universal APK — measured 2026-07-28: AAB 138.6 MB on disk (70.3 MB of that is debug symbols Play does not ship), per-device download 35.0 MB arm64 / 34.6 MB arm32, well inside the 200 MB base-module limit.
- If a `flutter run` is killed mid-build on Windows, the next Gradle run can fail with a file-lock `IOException` on `app\build\...`. Fix: `cd app/android && ./gradlew.bat --stop`, then delete `app/build`, then retry.

## Architecture

```
Flutter App ──HTTPS/JWT──► FatVPN BFF (.NET 10) ──Bearer──► Remnawave panel
                                    │                         (z.fatvdsnvv.space)
Telegram Bot ──X-Bot-Secret──► /internal/tokens
                                    │
                              PostgreSQL :5433
```

### API Endpoints

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/health` | none | Health check — now backed by a `DbContext` check (`ok` / `degraded`) |
| POST | `/internal/tokens` | `X-Bot-Secret` header | Bot registers short-token → Remnawave subscription ID |
| POST | `/internal/pair/complete` | `X-Bot-Secret` | Bot completes pairing by code → binds Account |
| POST | `/internal/account/subscription` | `X-Bot-Secret` | Bot upserts an account's current subscription (create/change/extend) |
| POST | `/auth/token` | none | App exchanges short token for access+refresh (legacy deep-link path) |
| POST | `/auth/refresh` | none | App exchanges refresh token for a fresh access (rotates refresh) |
| POST | `/auth/logout` | none | Best-effort refresh-token revocation (always 204) |
| POST | `/trial` | none | Grants a trial: creates a Remnawave user on the fly, returns access+refresh |
| POST | `/pair/start` | none | App starts pairing; returns pairCode + pollToken |
| GET | `/pair/status` | pollToken (query **or** `X-Pair-Poll-Token` header) | App polls until the bot completes pairing (returns access+refresh) |
| GET | `/servers` | JWT Bearer | Country-grouped Remnawave node list, cached 45 s (402 if subscription lapsed) |
| GET | `/me` | JWT Bearer | Subscription status/expiry (`status` is only ever `active` or `expired`) |
| GET | `/config` | JWT Bearer | Remnawave subscription, with our Hysteria2 hosts spliced in (402 if lapsed) |

Every public endpoint is rate limited per IP (`RateLimiting:*` — 300/min global, 20/min auth, 60/min `/pair/status`, 5/hour `/trial`) and answers **429 + `Retry-After`** over budget. A failed panel call is **502**, not 500. Full contract, including the required and optional configuration keys: `docs/api-contract.md`.

### Key Design Decisions

- **Bot auth**: Telegram bot calls `/internal/*` with a shared secret (`Bot:Secret`). The app never talks to Remnawave directly.
- **Session tokens (access + refresh split, see `docs/api-contract.md` "Модель токенов")**: A session is a short access JWT (**30 min**, `Jwt:AccessTokenLifetime`) plus a long, revocable, rotating refresh token (**90 days**, `Jwt:RefreshTokenLifetime`, stored hashed as `RefreshToken`). The JWT lifetime is **decoupled** from the subscription; entitlement is checked live per request, and `/config`/`/servers` return **402** when the subscription has lapsed (vs 401 for a bad token). The app refreshes silently, so an extension or key change never forces re-pairing. **Reuse detection**: presenting an already-revoked (rotated/logged-out) refresh token revokes the whole session family, forcing a re-pair (`AuthController.RevokeFamilyAsync`) — **except inside `Jwt:RefreshGraceWindow` (30 s)**, where a second presentation is treated as the app racing itself and is answered with another token of the same family. A "family" is the rotation chain of one sign-in (`RefreshTokens.FamilyId`, 2026-07-29), **not** the account: with one key on three phones, the phone that replays a spent token no longer signs the other two out. Rotation itself is one conditional `UPDATE`, so two parallel refreshes can no longer both succeed. The client should always keep the **last** refresh token it received.
- **JWT claim**: `fatvpn_account_id` (pairing sessions) or `fatvpn_token_id` (legacy deep-link / trial) identifies the session; the BFF resolves the current Remnawave subscription live on each request (`SubscriptionResolver`).
- **Pairing**: The app is the entry point — `POST /pair/start` → user opens the bot via `t.me/<bot>?start=pair<code>` → bot calls `/internal/pair/complete` → app polls `/pair/status` and connects. `Account` (keyed by Telegram user id) holds the current subscription, kept fresh by the bot. Pairing codes are **single-use**: `/pair/status` mints the session once, then flips the code to `Consumed` (`PairingStatus`) so a repeated poll can't hand out a second session; `/internal/pair/complete` only accepts a `Pending` code (409 otherwise).
- **Which key the app runs on** (2026-07-28): a user can hold several keys in the bot while the account carries exactly one active subscription, so every write says whether the user *chose* this key. Pairing and pasting a "Код для FatVPN App" are both explicit choices and both now produce an **account** session: `/internal/tokens` takes `telegramUserId` and stamps `Tokens.AccountId`, and `/auth/token` for an owned key writes that key into the account and issues `fatvpn_account_id`. Everything else (`/internal/account/subscription` without `makeActive`) only refreshes the key that is *already* active — extending key #2 used to drag a subscriber off key #1. Before this, a pasted key resolved through the `Tokens` row alone, which the bot only rewrites on reissue: extending a subscription left the app on "expired" and answered 404 to the user's own key. Keys with no owner (older bot builds, trial keys) behave exactly as before. The bot half is written too — pairing now asks *which* key when the user holds several, instead of silently taking the longest-lived one. Reading the live bot turned up something the spec never mentioned: merely *opening* a key's screen called `upsert_subscription`, so browsing your keys moved the app onto whichever you looked at last; that is what `replacesSubscriptionId` and the "an already-lapsed key is not worth protecting" rule exist for. **Both halves are deployed (2026-07-28)** and verified end-to-end against the live stack — pasting a code, switching keys, and a session surviving a key change all check out. Bot sources live only in `/opt/FatVPN/bot`, originals kept as `<file>.pre-keychoice`. Full record: `docs/app-bff-integration.md`; the Telegram-side checklist in `docs/bot-pairing-spec.md` §"Доработка 2" has **not** been walked by hand. ~~The Flutter changes (404 message on a bad key, pairing surviving process death) are still uncommitted and need an APK build.~~ Stale — verified against `HEAD` on 2026-08-03: both are committed (`strings.dart` carries `keyNotFound` in both locales, `token_storage.dart` persists `pending_pairing`). What is still true is the second half: neither has been in an APK on a device.
- **One key, up to 3 devices** (2026-07-29, employer request): pasting a key used to bind it to the first phone (`Tokens.BoundDeviceKeyHash`) and answer **409** to every other. It now takes one of `Auth:MaxDevicesPerKey` (default **3**) numbered slots in the new `TokenDevices` table; a device already holding a slot re-enters as often as it likes, and the fourth gets 409 with `{"error":"device_limit"}` so the app can say "already on 3 devices" instead of the misleading "linked to another phone". **The cap is enforced by the unique index `(TokenId, SlotIndex)`, not by a count** — counting rows and then inserting lets every racer read "room for one more", which is exactly what the Testcontainers tests caught when the first attempt used a counter column (8 racing devices got 4 in). Reissuing the key in the bot frees all slots. Pairing stays uncapped. Legacy builds that send no `attestationToken` still get a session without taking a slot. `BoundDeviceKeyHash` is kept-and-ignored so a rollback to the previous image still works; the migration backfills each bound key into slot 0. **Deployed to prod and re-checked on the live server** (2026-07-29/30) — the "not deployed" note that used to stand here was stale, and re-verified on 2026-08-02 from outside: `POST /pair/start` accepts the `attestationToken` body the per-subscription slots introduced, and the policy routes from `3b21cac` (the newest commit touching `backend/`) answer 200, so the server is on current `master`. What followed the same week is the more important half: the fourth device now **evicts the least recently seen** one and logout frees a slot, and the slots hang off the **subscription**, not the key code — pairing did not count them at all, and the bot mints a fresh code every time it shows a key screen, so the limit had two ways around it. See the `project-device-slots-eviction` memory for the traps (Npgsql stores `DateTimeOffset.MinValue` as `-infinity`; read `AsNoTracking()` after `ExecuteUpdate`).
- **Trial**: `POST /trial` creates a Remnawave user on the fly (squad `Remnawave:TrialSquadUuid`, `Trial:DurationDays`, currently 2). Anti-abuse: `Device` stores a salted hash of the `attestationToken`; the token must be **16–512 chars** (an empty one hashed to the same identity for everybody and handed the first caller's trial to every later one), and the endpoint is capped at 5/hour per IP. A device whose trial is still running gets its session **reissued** (200); 409 only once the trial is spent. ⚠️ The token is a random per-install key — reinstall = new trial; real Play Integrity / SSAID binding is still TODO (see `docs/api-contract.md`).
- **Remnawave subscription proxy**: `/config` returns the panel's response with our Hysteria2 hosts appended — Remnawave renders them into no subscription format we consume, so `SubscriptionAugmenter` synthesizes the links itself (hosts in `Remnawave:HysteriaHosts`, on by default via `Remnawave:AugmentHysteria`). Otherwise it is passed through as-is (currently base64 `vless://` URIs); sing-box JSON format would require configuring templates in the Remnawave panel.
- **IPv6 is blocked, and blocking it requires an address** (2026-08-02, Android; iOS since 2026-07-28): the TUN carries a ULA `fdfe:dcba:9876::1/126` on both platforms, and `route.rules` sends `::/0` to `block`. The address is not a feature — it is what makes the rule reachable. An OS routes nothing of a family the tunnel interface holds no address for, so with an IPv4-only TUN the whole v6 half of the device's traffic went around the tunnel in the clear, with the user's real address, while the block rule sat in the config looking like protection. A DNS-leak test cannot see it, because DNS is not what leaks. **The Android MTU moved 1100 → 1280 with it and not for throughput**: an interface below the IPv6 minimum link MTU cannot hold an inet6 address at all, so "1100 + inet6" would be a tunnel that reads as fixed and leaks exactly as before — the worse failure, because the config would say otherwise. The invariant "any platform with a v6 address has MTU ≥ 1280" is pinned by `ios_audit_ipv6_leak_test.dart`, and the Android native side needed no change (`VpnTunBuilderConfigurator` already reads `inet6Address` out of libbox's `TunOptions`). ⚠️ **The leak was never reproduced** — inferred from six snapshots of the live Android config, on an emulator that most likely has no IPv6 — and neither the fix nor the new MTU has been on a device. Acceptance is TA14–TA16 in `docs/release-test-checklist.md` §2e; until then the honest claim is "the interface now has an address for the family", not "the leak is gone", and 1280 is a change to how packets move on the one platform that was device-tested.
- **Tracker protection** (2026-08-02, employer asked for an ad blocker): a Settings switch, off by default, that drops ~250 ad/tracker domain suffixes inside the tunnel — one `domain_suffix → block` route rule fed by `TrackerBlockList` (`app/lib/services/tracker_block_list.dart`) through the new `RouteOptions.blockedDomainSuffixes`. **The list is compiled into the app, not fetched.** sing-box's remote `rule_set` is a *start-time dependency of the router*: the download happens before there is a tunnel, from a network that is usually why the VPN was installed, so a failed fetch would mean "switching this on stopped the VPN from connecting" — and on iOS `cache_file` is off (`memoryLimit`), so it would re-download on every connect. The plugin's `SingboxRuleSet` remote model stays unused; if auto-update is ever wanted, do it from Dart in the background, never in the start path. **Rule order is the feature:** the block rule is emitted *above* the `direct` rules, because `yandex.ru` is seeded into the bypass list automatically and `mc.yandex.ru`/`an.yandex.ru` are suffixes of it — placed after, the switch would silently do nothing on the largest ad network its users meet. That guarantee lives in `packages/singbox_mm/test/tracker_block_rule_order_test.dart`, at the plugin, since the app can no longer produce the combination. **Named for tracking, not ads, on purpose:** Google Play's Device and Network Abuse policy bars apps that interfere with third-party ad serving (Adblock Plus, Blokada were removed under it) while VPNs that filter for privacy are accepted — so the rename is sweeping, down to names in the binary, because Play's automated review reads APK contents. The UI subtitle still says ad networks are blocked; the framing is for the store listing, and the remaining risk lives in that listing's text, not in code (`docs/store-compliance.md` §3.1a). **Mutually exclusive with split tunneling** (employer's call): each switch turns the other off and gives it back — including its rules and mode — when released, with the marker persisted so "and back again" survives a restart. That removes the question of what a bypass entry means when the blocklist is matched ahead of it. ⚠️ On Android the cost is real: an app the user deliberately kept out of the VPN lands *inside* it the moment protection goes on, which reads as the app breaking, so the explanatory subtitle under the disabled switch is load-bearing. The split-tunnel master switch moved out of `SplitTunnelHeader` into the Settings ROUTING card at the same time. **Both switches were then run on an Android emulator (2026-08-02, Pixel 7 / API 35, live trial session, real nodes)** and the routing checked against `files/singbox/active-config.json` of the running tunnel rather than against the UI: TA1–TA4 and TA8–TA13 pass, and split tunneling is confirmed behaviourally — an excluded Chrome reported the host's own public IP, and the moment tracker protection took over it reported the VPN exit, which is exactly the risk the mutual exclusion carries. Three defects came out of that run, two fixed in place. **The block list was missing `yabs.yandex.ru`** — the host Yandex Direct actually serves from — so on `ya.ru`, the one page a Russian user is most likely to test on, the switch looked inert; `an.yandex.ru` covers only the older delivery path. **`AppLogger.e` threw on every error it was handed**: `IOSink.flush()` binds the sink until its future completes, `e()` writes message-then-stack, and the message starts the error flush, so the stack always landed inside that window. Since `main()` calls `log.e` from `FlutterError.onError`, the throw happened *inside the error handler* — the framework error never reached the console, the file or the support bundle, and the frame it was raised in was abandoned. It showed up as **a blank split-tunnelling screen** with nothing in the log to explain it; underneath was a harmless debug-only `ListTile` assert (still there, not chased). Pinned by `app/test/app_logger_error_flush_test.dart`. 277 app + 212 plugin tests, analyze clean — but note that `audit_best_node_test.dart` "candidates are measured concurrently, not one after another" is **flaky on a slow machine**: it failed in one full run and in isolation, passed in the next full run, and behaved identically with these changes stashed. It measures wall-clock overlap, so treat a single red run of it as noise and re-run before chasing it. Still unproven: everything an emulator cannot be — network switches, doze, the OS revoking VPN consent — plus non-Yandex ad networks and TA5's app-by-app sweep. Acceptance and the full result table: `docs/release-test-checklist.md` §2d. Separately answered for the employer: there is **no telemetry anywhere** in app or BFF, so "how many people use it" cannot be seen and would need a deliberate, store-declarable addition.
- **Certificate pinning is to the CA, not to the server's key** (2026-08-02, `app/lib/config/ca_pins.dart` + `createBffHttpClient`): the app's only HTTP client is built on `SecurityContext(withTrustedRoots: false)` holding the four current ISRG roots, so the device's ~150 stored CAs — and, on iOS, any CA a configuration profile installs — can no longer vouch for `api.fatklyuchi.space`. **A pin on the leaf key was rejected on purpose**: Caddy's certmagic mints a new key on every renewal (~60 days), there is no remote switch to disable a bad pin, and the fix would be a store release — days on iOS. Anchors move on a scale of years with public notice, and all four roots are bundled, so renewals, a new intermediate and an RSA↔ECDSA switch all pass unnoticed. Verified from the dev machine, not a device: the live domain answers 200 under this trust store using the same Dart/BoringSSL stack the app uses, while `google.com` under it throws `HandshakeException` — the system roots really are gone. `test/ca_pinning_test.dart` stands up a real TLS server holding a foreign CA's certificate and requires the refusal, and fingerprints the bundle against what letsencrypt.org publishes so the file cannot be edited quietly. ⛔ **The operational contract is the dangerous part**: changing the domain's CA (ZeroSSL, a Cloudflare origin certificate, anything not ISRG) takes every installed build offline until a new one ships — a new root goes into the app and out to users *first*, the server changes second. Renewals need nothing. Acceptance is TA17–TA19 in `docs/release-test-checklist.md` §2f, and TA17 ("the app still works at all") gates shipping any build carrying this. What it does not stop: a Let's Encrypt certificate issued for our own name — whoever controls DNS in the customer's Cloudflare could get one, but they could equally repoint the record, so the pin loses nothing there.

### Production Server (87.121.221.229)

| Component | Path | Container |
|---|---|---|
| BFF | `/opt/fatvpn-bff/backend/` | `fatvpn-bff` (**public** `0.0.0.0:5030`, HTTP — see below) |
| Caddy | same compose | `fatvpn-caddy` (`80`/`443`, TLS for `api.fatklyuchi.space`) |
| Bot (Python) | `/opt/FatVPN/` | `fatvpn-bot` |
| Postgres | — | `fatvpn-postgres` (`127.0.0.1:5433`, localhost-only) |

> **HTTPS is live (2026-07-30): `https://api.fatklyuchi.space`.** Caddy runs beside the BFF in the same compose and holds a Let's Encrypt certificate; `http://` redirects to it. The domain is the customer's, in **their** Cloudflare account, delegated to Cloudflare nameservers — but every record is **`DNS only` (grey cloud), and must stay that way**: the free proxy passes only HTTP/HTTPS on its own port list and no UDP at all, so an orange cloud kills VLESS on a non-standard port and Hysteria2 (QUIC) outright. That is what took the nodes down the one time it was tried. `sub.fatklyuchi.space` is separately fronted by **Yandex Cloud CDN**, not Cloudflare.
>
> Plain `http://87.121.221.229:5030` is **deliberately still open**: builds already on people's phones point at it. Retire it only once every shipped build uses the domain — a new APK is not enough, the old ones have to be gone.
>
> `ufw` allows `22`/`80`/`443`/`5030`/`4444`. Postgres is bound to localhost. The checkout is on `master`; deployment config (`docker-compose.yml`, `Caddyfile`) is tracked, and only `.env` is local — so `git pull` on the server is clean.

Docker network `fatvpn_default` is shared between `fatvpn-bot` and `fatvpn-bff` so the bot reaches BFF via `http://fatvpn-bff:5030`. The network is declared in both compose files — no manual `docker network connect` needed after restarts:
- Bot compose (`/opt/FatVPN/docker-compose.yml`): `networks.default.name: fatvpn_default`
- BFF compose (`/opt/fatvpn-bff/backend/docker-compose.yml`): `networks.fatvpn_default: external: true`, bff service connected to both `default` and `fatvpn_default`

`BOT_SECRET` is set in BFF container env (`Bot__Secret`), not in a file — retrieve with `docker inspect fatvpn-bff`.

⛔ **Set `TRIAL_DEVICE_KEY_SALT` before the next deploy.** Startup now validates configuration
(`ValidateOnStart`) and **refuses to boot** outside Development without `Trial__DeviceKeySalt`,
`Jwt__Secret` (≥32 bytes), `Bot__Secret` (≥16 chars) and `Remnawave__ApiToken`. `docker-compose.yml`
passes the salt as `${TRIAL_DEVICE_KEY_SALT}`; without it the container crash-loops. Full list of
required and new optional settings: `docs/api-contract.md`.

`appsettings.Development.json` is no longer tracked in git (template: `appsettings.Development.example.json`)
— treat the secrets it used to hold as public, and note the app now refuses to run the Development
configuration on a non-loopback address.

✅ **Server hardening done (2026-07-06):** Postgres moved to `127.0.0.1:5433` (BFF compose), `ufw` enabled (`22`/`5030`/`4444`). Postgres creds are still weak (`fatvpn`/`fatvpn_dev`) — rotate before real prod. Note: Docker-published ports bypass `ufw`, so the BFF (`5030`) stays reachable regardless; the real protection for Postgres is the localhost bind.

⚠️ **Fixed a pre-existing bug (2026-07-06):** `/opt/FatVPN/docker-compose.yml` had a duplicated `networks:` key — `docker compose` v2 refused to parse it, silently blocking bot redeploys. Removed the duplicate (backup at `/root/bot-compose.yml.bak`).

Deploy BFF: `cd /opt/fatvpn-bff/backend && git pull && docker compose build --no-cache bff && docker compose up -d bff`  
Deploy bot: `cd /opt/FatVPN && docker compose build --no-cache && docker compose up -d --force-recreate`
